第一次认真数生产机上的容器，是排查一次录音失败的时候。`docker ps` 拉出来三十一个，滚了满屏。一台八G内存的坏电池笔记本，跑出一个中型机房的阵仗，怎么看都像失控了。

先拆穿这个数字。三十一个里面，二十六个跑的是同一个镜像、同一个二进制，读同一份配置文件，区别只有一条启动命令：这个容器跑 `qq run`，那个跑 `schedule run lecture`，另一个跑 `jwxt run`。剩下五个才是别的软件，一个规则代理，一个语音识别，一个共享的无头浏览器，还有两个属于另一个项目。

所以真正的问题不是「为什么这么多容器」，是一个进程能干的活，为什么要拆成二十六个进程。这篇把这笔账算清楚：机制怎么搭，为什么拆，拆的边界在哪，代价付了多少。中间有一次真实事故，正好把这套路子最薄弱的一环掀了出来。

## 一个镜像，多种活法

机制没什么玄机。compose 文件里先用锚点把公共部分钉住，每个服务只写自己不一样的地方：

```yaml
x-ru41: &ru41-common
  image: ru41:local
  init: true
  restart: unless-stopped
  environment:
    RU41_CONFIG: /etc/ru41/ru41.toml
    RU41_DB: /data/state.db

services:
  qq:
    <<: *ru41-common
    profiles: [qq]
    volumes: *ru41-volumes
    command: ["--config", "/etc/ru41/ru41.toml", "--db", "/data/state.db", "qq", "run"]

  rss:
    <<: *ru41-common
    profiles: [rss]
    volumes: *ru41-volumes
    command: ["--config", "/etc/ru41/ru41.toml", "--db", "/data/state.db", "rss", "run"]
```

镜像本身也是一份多用。Dockerfile 分三个阶段：Rust 阶段编主程序，第二个阶段把十几个插件的 .so 一起编出来，最后的运行时不是什么极简底座，是 node 的 slim 镜像，因为 agent 底座 Codex CLI 是个 npm 包。ffmpeg、pandoc、libreoffice 这些工具也装在运行时里，谁的任务用得上谁取。部署文档里写了原则：主镜像不背无头浏览器和大模型，重依赖按独立镜像增加，不影响主镜像。

profiles 保证没配置的功能不会被 `docker compose up` 全部拉起，容器里加载哪些插件还能用环境变量白名单再滤一层。这套机制的要点用一句话概括：一个镜像走天下，容器是进程的边界，不是软件的边界。

## 为什么要拆

理由有四个，每个都不是从架构书上学来的。

最疼的一条：插件是动态库，panic 会拖死整个进程。附属功能全部以 .so 插件挂载，插件和宿主共享进程空间，插件里一个 Rust panic 触发的是整个进程的 abort。实际发生过，插件里的异步任务跑错了运行时，一句 no reactor running 把宿主进程直接带走。假如 QQ 网关、课表提醒、录音转写全在一个进程里，这种崩溃就是全家陪葬。拆开之后，崩的只是一个容器，docker 按重启策略拉起来，别的模块连感知都没有。

第二条是滚动更新。图书馆插件改一行，重建它自己那一个容器就行，QQ 网关不用断线重连。单进程形态下，任何改动的生效都要重启整个进程，重启就意味着掉线和中断手头的任务。

第三条是资源。哪个模块死循环了，烧的是它自己容器那份 CPU，`docker stats` 一眼定位。

第四条是挂载面。笔记仓库只挂给真正需要的容器，爬虫的 cookie 目录只有爬虫容器看得见。这条目前执行得不算严，不少容器挂的还是全量数据，但边界至少画出来了。

有人把这种拆法叫去中心化，其实不是。三十一个容器挤在同一台机器上，共用同一个 docker daemon，中心化得很。拆开改变的不是权力结构，是故障半径。

## 为什么不塞进一个容器

最容易想到的省事方案：一个容器跑二十六个进程，找个 supervisor 管着。技术上完全成立，但这么干会把 docker 的两个核心能力扔掉。

一是自动重启。`restart: unless-stopped` 盯的是容器主进程，supervisor 占着这个位置，里面某个子进程崩了，docker 看不见，不会拉起。二是归因。一进程一容器，`docker ps` 扫一眼就知道谁活着谁挂了；塞进一个容器，就得自己再造一套进程状态管理，等于手工复刻一个功能更差的 docker。

所以二十六个容器这笔账，本质是拿 docker 现成的进程管理，换二十六份隔离和二十六份自动拉起。内存多花一点，二十六个 Rust 进程各自加载一份插件，换来的是半夜崩溃时只有一门功能哑掉，而不是整个机器人失联。

## 名单是谁的

这套路子里最值得写的争论，是容器和插件的对应关系归谁管。

插件声明的是活。每个插件的注册表里写着自己有什么定时任务、多久跑一次：

```rust
pub static DEF: ModuleDef = ModuleDef {
    name: "lecture",
    schedule: |config| {
        let lecture = config.sources.get_or_default::<LectureSection>("lecture");
        vec![JobSchedule::simple(
            "lecture",
            LectureSection::DEFAULT_INTERVAL_SECS,
            lecture.is_ready(),
            lecture.not_ready_reason(),
        )]
    },
    // ...
};
```

部署决定的是这个活给谁跑。很长时间里，这是一份手写在滚动脚本里的名单，每个容器名对应一个启动命令，新建附属要人肉往名单里加一行。

两层各管各的，中间没有任何自动机制。这个断层迟早出事，出事的方式也很有代表性：lecture 是后来加的附属，没人把它加进名单，于是每次滚动更新都轮不到它。别的容器都换到新镜像了，它还钉在几代之前的旧镜像上，最后在崩溃循环里躺了半天，还是排查录音失败的时候顺带发现的。一个本该「新附属上线即被覆盖」的机制，实际依赖的是人的记性。

修法是把名单删掉。滚动脚本改成自动发现：

```bash
while read -r name; do
  [[ "$name" == ru41-* ]] || continue
  ep="$(docker inspect "$name" --format '{{json .Config.Entrypoint}}' 2>/dev/null || true)"
  [[ "$ep" == *"/usr/local/bin/ru41"* ]] && NAMES+=("$name")
done < <(docker ps -a --format '{{.Names}}')
```

识别规则只有两条：名字以 ru41- 开头，entrypoint 是 ru41 本体。满足就进滚动名单，镜像被钉成无标签 ID 的掉队容器也能凭 entrypoint 认回来。重建之前，每个容器的完整 inspect 存进带时间戳的备份目录，env、挂载、网络逐字段恢复，回滚就是拿备份重建。改完之后，新附属只要起了容器，下一次滚动自动覆盖，名单这个词从部署里消失了。

这段经验说穿了很朴素：声明和执行之间只要隔着一份手抄的东西，这份手抄迟早过期。

## 拆出去的另一半

自家那二十六个容器是「一个镜像跑多种活」，机器上剩下的几种走的是另一条路：真拆出去。

判断标准出乎意料地一致：协议死了才拆。智慧树的接口层是加密加浏览器环境，直连走不通，就拆一个 Playwright 加虚拟显示的采集容器，它登录、枚举作业、写出一个 report.json，主程序只读这个文件，不碰智慧树的网络协议，也不持有账号密码。学习通正好反过来，调研发现协议层活着，签到、作业、图书馆全部 Rust 直连，一个容器都不用加。boss 直聘的爬虫单独一个 Python 镜像，因为它要浏览器自动化，跟主程序的运行时是两个世界；它甚至不常驻，重启策略是 no，宿主机的定时任务每天点两次名，爬完就退。

所有需要浏览器的活共享同一个 browserless 容器，HTTP API 直连，不再各自背一套 chromium。契约全部是最小的文件或一个接口：报告文件挂了，只影响当轮作业数据的新鲜度，机器人其他功能照跑；爬虫的凭证目录主程序容器看不见，出事也出在它自己的地盘。语音识别那组容器是录音那篇的老熟人，sherpa 加 int8 模型，接口对齐之后插件侧改一个地址就能换模型。对这台机器来说它们和爬虫是一类东西：跟主程序没有共享状态，只有一条窄窄的数据通道。

## 代价

拆不是免费的，账要摊开看。

日志是第一个撞上的。二十六个容器的日志没有总视图，排障要 `docker logs` 一个个翻。认真调研过企业级方案，结论是那套东西伺候不起，Elasticsearch 光自己就要两个G内存，在这台机器上比功能优先级还高。现在的路线是先装个轻量的日志聚合容器应急，Loki 加告警的完整方案打算做成一个附属插件，告警直接走 QQ。目前还没做完，这是欠着的债。

内存是第二笔。二十六份插件加载叠加在八G内存上，跟模型容器、浏览器容器挤同一个池子。选型时内存是硬红线，官方 SenseVoice 镜像空载就要一点五个G，在这台机器上根本没资格常驻，最后落地的 int8 方案四百五十 MB。这不是节俭的美德，是被硬件逼出来的取舍。

配置一致性是第三笔。全机共享一份配置文件，容器各有各的启动时机，配置改了要重启对应容器才生效。录音管道那次故障的根因就是配置里一个段丢了，进程不知道，人也不知道，直到一条四十二兆的录音掉进错误的管道才暴露。

镜像分发是第四笔。服务器没有公网，CI 构建出镜像后不走 registry 拉取，本机拉下来打包，ssh 管道灌进去，再滚动重建。多一步人肉搬运，但三十一个容器共享一个镜像，搬的也就只是一份包。

## 账怎么算

回头看，二十六个容器不是设计出来的，是被三类现实逼出来的：插件会崩，更新不能断网，硬件只有一台。单进程形态每一项都更优雅，优雅的代价是任何一个插件出事全家陪葬。个人系统评判架构的标准跟公司不一样，公司看吞吐和协作，个人系统只看一件事：半夜三点它坏了，被吵醒的你面对的是一个容器的日志，还是三十一个。

现在这台机器上，`docker ps | grep -c Up` 的答案是三十一。每个容器背后都对应一次具体的翻车，这个数字还会涨，涨到哪天内存见顶，再考虑合并的事。
