录音失败那次排查，我在生产机上跑了 `docker ps`，三十一个容器滚了满屏。一台八G内存的坏电池笔记本，摆出中型机房的阵仗。只看这一屏，很容易以为我在搞分布式，其实它是一台机器。

再看仔细一点会发现大部分容器是重复的。二十六个跑着同一个镜像、同一个二进制，读同一份配置，区别只有启动命令：这个跑 `qq run`，那个跑 `schedule run lecture`，另一个跑 `jwxt run`。剩下五个才是别的软件，一个代理，一个语音识别，一个共享的无头浏览器，两个属于另一个项目。

## 一开始它就是一个进程

ru41 最早是单进程。一个 Rust 程序，QQ 网关、定时任务、十几个模块的业务全在里面。这个形态舒服得实打实：内存只有一份，日志只有一份，`cargo run` 一条命令就是全部部署。要不是后来出事，大概会一直这么跑下去。

出事是因为架构里有个前提站不住：插件是 .so 动态库，跟宿主共享进程空间，插件里的 Rust panic 触发的是整个进程的 abort。某天一个插件里的异步任务跑错了运行时，一句 no reactor running 把宿主进程带走。QQ 掉线，定时任务全停，正在转写的录音中断，所有功能同一秒死掉。

这次之后我不再相信「一个进程管所有模块」。理由很具体：插件不是我写的全部代码，它们的崩溃我拦不住，能选的只有崩溃发生的时候倒多大一片。

## 拆，但不是塞进一个容器

崩溃隔离的答案是多进程，最省事的形态也摆在那里：一个容器跑二十六个进程，找个 supervisor 管着。技术上完全成立，我没用它，因为它把 docker 的两个核心能力扔掉了。`restart: unless-stopped` 盯的是容器主进程，supervisor 占着这个位置，里面某个子进程崩了，docker 看不见，不会拉起。归因也变糊了，一进程一容器，`docker ps` 扫一眼就知道谁活着谁挂了；塞进一个容器，就得自己再造一套进程状态管理，等于手工复刻一个功能更差的 docker。

拆完的样子是二十六个容器、一个镜像。compose 里用锚点钉住公共部分，每个服务只写自己不一样的那一行：

```yaml
x-ru41: &ru41-common
  image: ru41:local
  init: true
  restart: unless-stopped
  environment:
    RU41_CONFIG: /etc/ru41/ru41.toml
    RU41_DB: /data/state.db

services:
  qq:
    <<: *ru41-common
    profiles: [qq]
    volumes: *ru41-volumes
    command: ["--config", "/etc/ru41/ru41.toml", "--db", "/data/state.db", "qq", "run"]

  rss:
    <<: *ru41-common
    profiles: [rss]
    volumes: *ru41-volumes
    command: ["--config", "/etc/ru41/ru41.toml", "--db", "/data/state.db", "rss", "run"]
```

镜像也是一份多用。Dockerfile 分三个阶段，Rust 阶段编主程序，第二个阶段把十几个插件的 .so 一起编出来，运行时不是什么极简底座，是 node 的 slim 镜像，因为 agent 底座 Codex CLI 是个 npm 包。ffmpeg、pandoc、libreoffice 装在运行时里，谁的任务用得上谁取。主镜像不背无头浏览器和大模型，重依赖按独立镜像增加。profiles 保证没配置的功能不会被 `docker compose up` 全部拉起，容器里加载哪些插件还能用环境变量白名单再滤一层。

顺带修好的还有几件单进程年代的旧毛病。图书馆插件改一行，重建它自己那个容器就行，QQ 网关不用断线重连，任何改动的生效都不再需要整个进程重启。哪个模块死循环了，`docker stats` 一眼定位，烧的也只是它自己那份 CPU。笔记仓库只挂给真正需要的容器，爬虫的 cookie 目录只有爬虫容器看得见，这条执行得还不算严，不少容器挂的仍是全量数据，但边界画出来了。

有人管这叫去中心化。不是的，三十一个容器挤在同一台机器上，共用同一个 docker daemon，中心化得很。拆开改变的不是权力结构，是故障半径：半夜崩了，哑掉一门功能，而不是整个机器人失联。

## 手写的名单

这套架构最薄弱的地方不在代码里，在部署脚本里。

插件这边，每个插件的注册表声明自己有什么活、多久跑一次：

```rust
pub static DEF: ModuleDef = ModuleDef {
    name: "lecture",
    schedule: |config| {
        let lecture = config.sources.get_or_default::<LectureSection>("lecture");
        vec![JobSchedule::simple(
            "lecture",
            LectureSection::DEFAULT_INTERVAL_SECS,
            lecture.is_ready(),
            lecture.not_ready_reason(),
        )]
    },
    // ...
};
```

部署那边，容器和活的对应关系是一份手写在滚动脚本里的名单，每个容器名对应一条启动命令，新建附属要人肉加一行。两层各管各的，中间没有任何自动机制。

这个断层真的出过事。lecture 是后来加的附属，没人往名单里加它，每次滚动更新都轮不到它。别的容器都换上新镜像了，它还钉在几代之前的旧镜像上，最后躺进崩溃循环，是排查录音失败那天顺带发现的。一个本该「新附属上线即被覆盖」的机制，实际依赖的是人的记性。

修法是把名单删掉，滚动脚本改成自动发现：

```bash
while read -r name; do
  [[ "$name" == ru41-* ]] || continue
  ep="$(docker inspect "$name" --format '{{json .Config.Entrypoint}}' 2>/dev/null || true)"
  [[ "$ep" == *"/usr/local/bin/ru41"* ]] && NAMES+=("$name")
done < <(docker ps -a --format '{{.Names}}')
```

识别规则只有两条，名字以 ru41- 开头，entrypoint 是 ru41 本体，镜像被钉成无标签 ID 的掉队容器也能凭 entrypoint 认回来。重建之前每个容器的完整 inspect 存进带时间戳的备份目录，env、挂载、网络逐字段恢复，回滚就是拿备份重建。改完之后新附属只要起了容器，下一次滚动自动覆盖，名单这个词从部署里消失了。

## 协议死了才拆

机器上另外几个容器走的是另一条路：真拆出去，跟主程序不是同一个软件。该不该拆，实践里收敛成一条标准：协议死了才拆。

智慧树的接口是加密加浏览器环境，直连走不通，就拆一个 Playwright 加虚拟显示的采集容器，它登录、枚举作业、写出 report.json，主程序只读这个文件，不碰智慧树的网络协议，也不持有账号密码。学习通正相反，调研完发现协议层活着，签到、作业、图书馆全部 Rust 直连，一个容器都不用加。boss 直聘的爬虫单独一个 Python 镜像，它要浏览器自动化，而且跟主程序一个 Rust 一个 Python，本就是两个世界；它也不常驻，重启策略是 no，宿主机的定时任务每天点两次名，爬完就退。需要浏览器的活共享同一个 browserless 容器，HTTP API 直连，不再各自背一套 chromium。

这类拆出去的容器跟主程序之间只有窄窄的数据通道，一个报告文件，一个接口地址。报告文件挂了，只影响当轮作业数据的新鲜度，机器人其他功能照跑；爬虫的凭证目录主程序看不见，出事也出在它自己的地盘。语音识别那组是录音篇讲过的 int8 容器，接口对齐之后插件侧改一个地址就能换模型。

## 拆开之后多出来的麻烦

日志最先撞上。二十六份日志没有总视图，排障要 `docker logs` 一个个翻。企业级方案调研过，Elasticsearch 光自己就要两个G内存，在这台机器上比功能优先级还高。现在的路线是先装个轻量的日志聚合容器应急，Loki 加告警打算做成附属插件，告警直接走 QQ，还没做完，欠着。

内存是明账。二十六份插件加载叠在八G上，跟模型容器、浏览器容器挤同一个池子。官方 SenseVoice 镜像空载就要一点五个G，在这台机器上没资格常驻，最后落地的 int8 方案四百五十 MB。不是节俭的美德，是硬件逼出来的取舍。

配置一致性也变脆了。全机共享一份配置，容器各有各的启动时机，配置改了要重启对应容器才生效。录音那次故障的根因就是配置里一个段丢了，进程不知道，人也不知道，直到一条四十二兆的录音掉进错误的管道才暴露。

镜像分发多了一步人肉。服务器没有公网，CI 构建出镜像后不走 registry 拉取，本机拉下来打包，ssh 管道灌进去，再滚动重建。好在三十一个容器共享一个镜像，搬的只是一份包。

有人问我为什么不合并回单进程，省内存也省日志视图。合并回去押上的是任何插件出事全家陪葬。个人系统评判架构的标准跟公司不一样，公司看吞吐和协作，我只关心一个问题：半夜三点它坏了，被吵醒的人面对的是一个容器的日志，还是三十一个。

现在这台机器上，`docker ps | grep -c Up` 的答案是三十一。这个数字每往上涨一格，背后都对应一次具体的翻车。它还会涨，涨到内存见顶那天，再谈合并。
