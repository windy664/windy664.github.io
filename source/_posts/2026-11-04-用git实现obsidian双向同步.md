我的笔记仓库有三个写入口：手机上的 Obsidian，电脑上的 Obsidian，还有一台宿舍服务器上跑着的机器人——它往仓库里写课表提醒的待办、整理好的课堂笔记、每天抓取的活动日程。三个口子同时写一个仓库，早期没有同步机制的时候，堆积和冲突全靠人肉收拾，手机上一份、电脑上一份、服务器上一份，谁也不敢删，谁也不知道哪份是新的。

后来定下一条规矩：仓库只有一份，放在服务器上，通过 git 和两端桥接。Obsidian 是源，其他一切是投影：博客发布、知识库重建、待办视图，全部变成「从这份仓库读点什么、生成点什么」的任务。这篇写的是这条同步链路怎么搭的，以及它上线之后处理的六场事故。机制没什么惊人之处，事故倒是各有各的死法。

## 一个工作区，两个进程

服务器那边，仓库是一份 git 工作副本，封装成一个 Rust 适配器，全部操作就是调 git 命令行。听上去土，但 git 命令行是唯一三十年不变预期的接口，自己写对象模型反而给自己挖坑。

第一个坑不在 git 本身，在进程。QQ 容器和 obsidian 容器是两个进程，但操作的是同一份工作区，两边同时提交就是竞态。解法是写操作前取一把跨进程的文件锁：

```rust
/// 对仓库级写操作取排他文件锁（flock，跨进程，同文件系统有效）。
fn locked<R>(&self, op: impl FnOnce(&Self) -> Result<R>) -> Result<R> {
    let lock_path = self.path.join(".git/ru41.lock");
    let file = File::create(&lock_path)
        .with_context(|| format!("cannot create {}", lock_path.display()))?;
    let rc = unsafe { libc::flock(file.as_raw_fd(), libc::LOCK_EX) };
    if rc != 0 {
        bail!("cannot lock {}", lock_path.display());
    }
    op(self)
}
```

锁文件放在 `.git` 里面而不是仓库根目录，这样 Obsidian 永远看不到它，也不会手贱把它同步走。

第二条纪律是提交身份。机器人的自提交一律带前缀，仓库的协作契约里写死了：`[ru41]` 开头的提交是机器干的，不要伪装成人工提交。这条规则看着洁癖，实际是排查时的生命线——出事故的时候，一眼能分清哪些改动是人做的、哪些是自动化干的。凭证不进配置文件，git credential helper 自己解决，仓库里永远搜不到 key。

还有个中文用户才懂的小坑：git 默认把非 ASCII 路径转义成带引号的八进制串，diff 输出就没法按目录前缀匹配了。一行 `core.quotepath=false` 解决，解决不了的那种「明明改了文件却匹配不到」的灵异现象多半是它。

## 每轮先对齐，再谈别的

同步核心是一个函数。每一轮先 `pull --rebase` 把本地未推的提交重放到远端之上，本地有领先就补推：

```rust
fn sync(&self) -> Result<SyncOutcome> {
    self.locked(|vault| {
        if let Err(error) = vault.git(&["pull", "--rebase", &vault.remote, &vault.branch]) {
            let conflicts = vault.conflict_files().unwrap_or_default();
            if conflicts.is_empty() {
                // 非冲突失败（网络、认证等）：中止 rebase，恢复原状。
                let _ = vault.git(&["rebase", "--abort"]);
                return Err(error).context("vault sync rebase failed (aborted)");
            }
            // 冲突现场保留，交给调用方（AI 合并）处理。
            return Ok(SyncOutcome::Conflict(conflicts));
        }
        let ahead = vault.git(&[
            "rev-list",
            "--count",
            &format!("{}/{}..HEAD", vault.remote, vault.branch),
        ])?;
        if ahead.trim() == "0" {
            return Ok(SyncOutcome::Clean);
        }
        vault.git(&["push", &vault.remote, &format!("HEAD:{}", vault.branch)])?;
        Ok(SyncOutcome::Pushed)
    })
}
```

这个函数的返回值设计比函数本身重要。它返回三种结局：干净、推了、冲突。前两种是好消息，第三种不是报错，是一个「现场」：冲突的文件列表原样保留，rebase 停在半路，等上层决定怎么处理。网络断、认证挂这类非冲突失败则照常报错，但报错前自动 abort，工作区恢复原样——失败不该留下半成品状态，下轮再来就是了。

为什么不让 rebase 冲突走自动 abort？因为冲突信息一旦丢弃，上层就只能看到「同步失败」，丢了全部上下文。保留现场意味着上层拿到的是「哪些文件、什么内容冲突了」，这才是能动手处理的形态。

## 冲突交给 AI 合并，但不信任它

冲突现场留下来了，谁来解？仓库里的笔记冲突几乎全是「两边各加了几行」这种语义并集，git 三路合并无能为力，剩下的路只有人肉。手机上解冲突的体验我不想再要第二次，于是把带冲突标记的文件全文交给大模型，提示词就一句：两侧取并集、去重、保持 markdown 结构连贯，相同修改只留一份。

模型输出不能直接落盘，要过三道闸：

```rust
/// 合并结果校验：无残留冲突标记、非空、不超过原文 3 倍（防模型复读暴走）。
fn validate(merged: &str, original: &str) -> Result<()> {
    if merged.trim().is_empty() {
        bail!("合并结果为空");
    }
    // 冲突标记是独占一行的 7 字符序列；setext 下划线等短串不误伤。
    for line in merged.lines() {
        let t = line.trim_end();
        if t.starts_with("<<<<<<<") || t == "=======" || t.starts_with(">>>>>>>") {
            bail!("合并结果残留冲突标记行 {t:?}");
        }
    }
    if merged.len() > original.len().saturating_mul(3) + 1024 {
        bail!(
            "合并结果异常膨胀（{} -> {} 字节）",
            original.len(),
            merged.len()
        );
    }
    Ok(())
}
```

三道闸各管一种翻车：模型把冲突标记原样抄回来（它没理解任务），输出空串，或者复读原文把它自己编的内容撑到十倍长。任何一道拦下来，rebase 直接 abort，通知人工来处理。另外只有 `.md`、`.markdown`、`.txt` 三种扩展名允许进 AI 合并，图片和二进制文件模型碰不了，直接走人工。

这套机制在设计文档里的定位写得很清楚：AI 合并只是省事，不是可信路径。它接手的是「两边各加了几行」这种低风险冲突，高风险的合并失败会被校验拦住退回人工。信任要按失败模式定价，不能按成功次数定价。

## 收件箱整理工删了一份五百行的文档

机制到这里讲完了，剩下的篇幅给事故，每件都比机制本身记得牢。某天早上收件箱入口不见了——Obsidian 里那个文件夹整个消失。排查结果：昨晚的收件箱整理 agent 把一份五百多行的产品设计文档当成待清理杂物删了。

删除这个动作本身不致命，致命的是它没被发现。随后的一个同步任务用 `git add -A` 把工作区所有改动裹进自己的提交，删除就这样被顺手提交了，全程没有任何告警。数据在，git 历史里都在，恢复是一分钟的事；难堪的是「删除被另一个任务的提交掩盖」这个链路——两个自动化互相掩护，把一场事故做成了静默。

修复分两层。提示词层给整理技能加了删除红线：只有两行以内的纯一句话待办允许删，其余文件只许移动不许删除。代码层的问题更普遍：任务用 `git add -A` 提交，会把工作区里跟自己无关的改动裹进自己的提交，这是误删被掩盖的帮凶，正解是任务只提交自己负责的路径。这条写给了核心组，改的是所有做同步类任务的模块。

## 移动文件就是发布

有了单一事实源，博客发布的入口变得非常朴素：把定稿从草稿目录移动进已发布目录，推送。没有发布按钮，没有中间队列，移动文件就是发布仪式的全部。发布器每五分钟轮一轮，对已发布目录做增量 diff，新增的 markdown 逐个校验后写进博客仓库推送，线上部署自动跟着走。

校验是 frontmatter 层的：title 必填，categories 必须是站点允许的单个枚举值，tags 不超过八个，`draft: true` 的文件直接拒绝。每条规则背后都有一次真实的误发布，比如草稿那条：

```rust
if front.get("draft").map(|d| d == "true").unwrap_or(false) {
    return Err("frontmatter draft=true，请改为 false 再发布".to_owned());
}
```

幂等靠游标加内容哈希。发布器记住处理到哪个提交了，每轮只 diff 增量；每个文件处理完记一个键，键里同时有路径和内容哈希：

```rust
fn done_key(path: &str, content: &str) -> String {
    use std::hash::{Hash, Hasher};
    let mut hasher = std::collections::hash_map::DefaultHasher::new();
    path.hash(&mut hasher);
    content.hash(&mut hasher);
    format!("v3|{path}:{:016x}", hasher.finish())
}
```

崩溃重启后同一文件不会被发布两遍；内容变了视为新文件重新处理。这个键的格式前缀是 `v3`，前两版各死于一次真实缺陷：只哈希路径的版本，同一文件改完内容再移回来就被当成已处理跳过；后来又发现 Obsidian 常用的块列表写法（`tags:` 换行 `- item`）解析失败导致误拒，误拒的文件也要标记已处理，不然每次轮询都拒绝一遍。每个版本号都是一次「发布器重复干活或者漏干活」的现场。

校验拦得住格式问题，拦不住仓库状态和人的意图对不上。有过一件这样的事：一篇我不想公开的文章上了线。查下来不是发布器越权，是文件真的有两份：草稿目录一份，已发布目录一份，并存。我的本意是「放进草稿」，但实际操作是复制而非移动（或者移动了但没同步成功），发布器看到的是已发布目录里那份还在，它没错，它只是如实反映了仓库状态。

这正是单一事实源的脾气：系统只认仓库里的状态，你的意图它无从知晓。处理方式也顺着这个逻辑走——把已发布目录里那份删掉，发布器检测到删除，自动从博客仓库下架。下架不是逆向发布，它和发布共用同一条 diff 通道：移出已发布目录等于删除，发布器按映射找到博客仓库里的目标文件删掉。映射表记着「vault 路径到博客文件名」的对应，历史上手工发布过的老文章没有映射记录，就从文件名的日期前缀兜底推导，推不出来的列出来请人确认，不瞎删。

## 线上七十三篇，仓库里只有四十一篇

用户反馈「博客好像有大量重复内容」。第一反应是发布器抽风把旧文章又发了一遍，查了博客仓库，文件名层面没有重复，四十一篇干干净净。抓线上存档页一对，线上显示七十三篇。差的三十多篇是之前改名清理掉的旧文章——线上根本没被清掉，一直挂着旧版本。

真相是部署卡住了。站点构建里有一个链接完整性校验，旧文章正文里的十六处内部链接还指着已删除的英文旧 slug，校验不过，部署中止。清理之后连续六次部署全部这么挂掉，Pages 一直服务着清理前的旧构建，新文章上不去，旧文章下不来。

这场案子最值得记的是那个校验本身。它是保命设计：宁可让旧站多挂几个小时，也不放死链上线。副作用是部署静默失败——没人盯着 CI，挂了六次才发现，靠的还是用户眼尖。修复分两半：按旧文件的标题对到新文件名（有七篇标题重写过，靠文件名关键词对上），十一个文件十六处内链批量替换；再把「推完必须看部署是不是绿的」写进流程。构建校验一条没改，该拦还拦，拦下来的应该是修好的东西，不是同一批东西拦六次。

部署恢复只解决了「发不出去」，漏发还有另一个来源。增量 diff 依赖游标和提交历史的连续性，但历史会被改写，目录会被整体移动，这些操作会让游标越过实际内容，出现「发布器以为自己处理过了，博客仓库里其实没有」的静默漏发。兜底是一道对账逻辑：每轮发布之外，把 vault 已发布目录的全部文件和博客仓库实际部署的文章按 frontmatter 标题比对，博客侧缺的补发。

比对按标题，不按文件名。注释里写着理由：标题是内容身份，文件名只是展示层，历史上有过手工提交和目录整理，文件名对得上才算数会把正常文章误判成漏发。这道对账上线后，游标从「必须精确」降级成「尽量精确」，错了有对账兜着。同步系统里把某个组件从关键路径上摘下来，往往比把它修到永远正确便宜得多。

## 入口不止一个

发布器霸占着博客仓库的写入口吗？不是。网页编辑、另一台机器、我自己手工推文章，都是合法路径。今天推两篇文章时就撞上了：远程已经有了机器人推的提交，我的推送被拒，rebase 一下再推。发布器面临同样的问题，所以它的推送逻辑里有一条硬规矩：提交前先 `pull --rebase`，push 无条件执行——上一轮推送失败时本地已经留下未推的提交，本轮没有新内容不代表远端同步了。真撞上内容冲突（两边同时编辑同一篇文章），中止报错交人工，文章文件名唯一，这个概率低到可以接受。

单写入者架构当然更简单，但把所有发布都收编到一个进程里，代价是这条管线成了单点：它挂了，没有任何人能发文章。保留多入口，把冲突处理交给 rebase，是拿一点复杂度换可用性。

往回写是入口的另一半。同步如果只有「机器人写、人看」，那只是单向广播。真正的双向是 Obsidian 里的操作能改变机器人的状态：待办视图里的勾选会写回任务数据库，勾了就是完成，取消就恢复；在任意笔记里随手写一行无锚点的 `- [ ] 事项`，机器人识别出来自动入库，还支持截止日期语法。笔记仓库不再是投影的终点，它本身是输入。这条双向通道修通之后，「在 Obsidian 里勾掉一个待办」和「在 QQ 里发完成」是等价操作，用哪个全看人在哪。

## 动不动关机的笔记本

同步链路里还有个不像同步问题的插曲。服务器是一台电池报废的旧笔记本，有段时间它动不动自己关机，排查过是不是机器人死循环。真凶是知识库重建：全量扫描加向量化，CPU 满载时间太长，笔记本热保护直接断电。修法朴素得可疑：给知识库重建加了三十分钟冷却，重建频率压下来，断电消失。性能问题以散热问题的形态出现，这在宿舍机房不是段子，是常态。

回头看，六场事故没有一场出在同步算法本身，全出在「以为一切正常」的地方：整理工以为自己删的是杂物，发布器以为自己处理过了，部署以为校验挂了等下次就好。同步系统的每个动作都会被重试、重放、并发触发，状态设计得让人分得清「做过了」和「没做」，内容哈希加版本化的键是最便宜的实现；游标和历史都会漂，所以永远要有一道按内容比对的对账兜底，它平时空转，但空转的每一天都睡得安稳。AI 合并的位置也顺出来了：它管九成的低风险冲突，剩下一成被闸门拦给人，这套分工比「AI 全自动」和「全自动不敢用」都值钱。

仓库还是那一个仓库，手机、电脑、服务器各连各的，谁也不用关心另外两个在干什么。同步这件事，最终形态就是没人再想起它。
