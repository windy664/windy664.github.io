想法很简单：上课录音，下课把文件丢给机器人，让它自己转写、自己整理、自己归档。学期末打开 Obsidian，每门课一份连续的课堂笔记，题型、方法、考试线索都在里面，复习直接问。

真做起来才发现，这个想法最难的部分不是整理笔记，是转写本身。云端的语音识别要么要钱，要么我手头的 key 根本调不动；本地的开源模型，一个个在「坏电池笔记本改的服务器」这种硬件上撞得头破血流。这篇记录的就是这条转写管线的全过程：它换过四套方案，死过三次，最后落在一个没有 torch 的 int8 容器里，一次 API 费用都不花。

## 入口：拦一条文件消息

整个入口没有一个命令。机器人拦的是自然消息：QQ 单聊里来了带附件的文件，扩展名在音频白名单里（m4a、mp3、wav、aac、amr、ogg、flac、wma、opus、3gp、aiff 一共十几种），就当作课堂录音接住。群聊不要，未绑定身份的不要，录音是个人学习资料。

接住之后第一件事不是排队，是当场下载。QQ 的文件链接带时效参数，攒一会儿就失效，所以 handler 里下载是同步做的，下完才写队列、才回执：

```rust
let size = match ru41::plugins::bridge(async move {
    worker
        .run_job(store, source, display_name, channel, target, msg_id)
        .await
})
.await
{
    Ok(size) => size,
    // 下载失败要回执（链接时效/网络故障用户需要知道并重发），
    // 不能只在服务端日志里留个 handle failed。
    Err(error) => {
        return Ok(Some(Reply::text(format!(
            "## 录音接收失败\n\n《{}》下载没成功：{error:#}\n\n\
             QQ 文件链接有时效，也可能是网络临时故障，请重新发一次。",
            audio.display_name(),
        ))));
    }
};
```

这段里的失败回执是后补的。最早下载失败只在服务端日志里留一行，用户那边看到的是石沉大海，发消息问就是「又失败了，也不说原因」。补上回执之后，用户至少知道该重发，而不是干等。

## 管道骨架：队列、切片、续跑

下载完的录音进一个文档队列，worker 每分钟轮一轮，每次只处理最旧的一条。状态机短得可怜：pending，然后 done 或 failed。failed 是终态，不自动重试，因为转写失败的常见原因（文件损坏、切片全空）重试也解决不了，改完删文档重投就行。

转写前先切片。ffmpeg 把原始文件转成单声道 16k 的 mp3，按十分钟一段切开。单声道 16k 是给 ASR 模型省计算，十分钟一段是让单次请求的体积可控。这里有个不起眼但很受用的设计：切片目录里已经有产物就直接复用，不重新转码。十分钟的课录成九十分钟，转码一遍要几分钟，中途挂了重跑，前面切好的片直接用，只有转写会重来。

```rust
/// 原始文件切片；已有切片则跳过（中断续跑不重复转码）。
fn ensure_slices(&self, raw: &Path, slices_dir: &Path) -> Result<Vec<PathBuf>> {
    let mut existing: Vec<PathBuf> = std::fs::read_dir(slices_dir)?
        .filter_map(|e| e.ok())
        .map(|e| e.path())
        .filter(|p| p.extension().is_some_and(|e| e.eq_ignore_ascii_case("mp3")))
        .collect();
    existing.sort();
    if !existing.is_empty() {
        return Ok(existing);
    }
    // ... ffmpeg -f segment -segment_time 600 ...
}
```

队列更新用乐观并发：带着读出来的版本号写回去，写失败说明有并发改动，本轮跳过。加上幂等键，进程重启、重复轮询都不会把一条录音处理两遍。

## 第一盆冷水：key 现成，是个误会

方案最早写的云端路线：智谱的 GLM-ASR，理由是「key 现成，还有额度」。

这五个字是拍脑袋写的。手头确实有智谱的 key，但那个 key 来自 Coding Plan，而 Coding Plan 只开放对话兼容端点，音频接口根本调不动。更讽刺的是，这个限制我之前踩过一次，还在主 Dockerfile 里专门写了注释：

```
# 智谱 GLM coding plan 只有 chat 兼容端点，codex ≥0.16x 移除了 wire_api="chat"
```

注释就在那儿，转头就忘。被问到「你之前不是说这个 key 没全权限吗，那生产上跑的是什么」的时候才想起来对账。教训现在写进了流程：凡是判断「现成可用」，先真的调一次接口验证，再写进方案。这次是多问了一句才拦住，不然等录音发出去、管道切过去，收到的是一摞 401。

云端路线就此划掉，转本地。

## 第二盆冷水：whisper.cpp 三天就死

本地第一个上的是 whisper.cpp，C++ 写的，无依赖，听起来是低配机器的良配。接进管线也顺，ASR 客户端做成两种接口风格，OpenAI 兼容的和 whisper.cpp 原生的，配置里换个字段就切换。

问题出在超长录音上。第一版 HTTP 客户端超时设的 180 秒，十分钟的长片在 CPU 上转写轻松超过这个数，请求被自己掐死，用户看到的就是「录音处理失败，不给原因」。把超时改成 900 秒后，错误消失了，但换来的是另一种难受：慢。CPU 上转写一段十分钟音频要等好几分钟，比实时还慢，一个小时的录音转完，课都下完了。

慢还能忍，方向错了没法忍。本地化方案早就说好了是 SenseVoice，中间拿 whisper.cpp 先顶着，结果顶着顶着就忘了切换这回事。判词很短：删掉，卸载，不应该存在。于是 whisper.cpp 从部署里整个移除，这条路径从「临时方案」变成「没发生过」。

## 第三盆冷水：官方镜像撞上坏电池笔记本

SenseVoice 是阿里开源的语音识别模型，中文效果好，官方提供 SenseVoice-Small 的 Docker 部署。调研到「官方提供 Docker」就上了。

镜像拉起来一看，里面有 torch。不是一点，是整个 PyTorch 运行时，光空载就吃 1.5 到 2 个 G 内存。而这套东西要跑的生产机是一台改造成服务器的笔记本：i3-8130U，双核四线程，8G 内存，电池报废，常年插电。这台机器上还住着十几个别的容器。

被打回的意见很直接：怎么还有 torch，考虑过这台机器什么配置吗，做之前没调研没评估吗。复盘下来这个批评成立：调研的终点画在了「官方有没有现成部署」，而不是「这台机器跑不跑得动官方部署」。硬件约束要放在选型的第一行，不是最后一行。

## 落地：把 torch 拆掉

正解是 sherpa-onnx：纯 ONNX 运行时，没有 torch，SenseVoice 有现成的 int8 量化版，模型文件下载即用，常驻内存几百 MB。

服务不长，核心是识别前的一段 Voice Activity Detection。SenseVoice 单次输入不宜超过三十秒，所以先用 silero-vad 把音频按语音活动切段，每段最长留了二十秒的余量，再逐段喂给识别器：

```python
def transcribe_samples(samples: np.ndarray) -> str:
    vad = sherpa_onnx.VoiceActivityDetector(
        vad_config, buffer_size_in_seconds=len(samples) / SAMPLE_RATE + 30
    )
    window = vad_config.silero_vad.window_size
    texts = []
    pos = 0
    while pos + window <= len(samples):
        vad.accept_waveform(samples[pos : pos + window])
        pos += window
    vad.flush()
    while not vad.empty():
        stream = recognizer.create_stream()
        stream.accept_waveform(SAMPLE_RATE, vad.front.samples)
        vad.pop()
        recognizer.decode_stream(stream)
        text = TAG_RE.sub("", stream.result.text).strip()
        if text:
            texts.append(text)
    return "".join(texts)
```

`TAG_RE` 那行是在清理 SenseVoice 输出里带的语言标签，`<|zh|>`、`<|EMO_UNKNOWN|>` 这类标记，正则抹掉即可。

结果可以写进选型总结：三百秒音频，二十四倍实时速度转完，峰值内存四百五十 MB。在 i3-8130U 的双核四线程上。慢吞吞的 whisper.cpp 和它之间的差距不是工程优化能弥补的，是换了一个量级的运行时。

落地过程的另一半是网络。宿舍网 GitHub 直连六十 KB 一秒，模型包下完得一个小时；走代理能到 750KB/s，但又发现 hf-mirror 的路径拼错时下回来的是二十九字节的错误页，得对着仓库文件列表核对路径。最后干脆全换国内源：apt 走清华镜像，pip 走清华镜像，模型走 gh-proxy。这些坑都固化在 Dockerfile 的注释里，下次重建镜像不用再踩一遍。

## 姊妹镜像：Paraformer 当对照组

SenseVoice 服务落定之后，又起了个姊妹容器跑 Paraformer-large，接口一模一样，还是那个 whisper.cpp 兼容的 `/inference`，插件侧只改一个 base_url 就能切换。两个模型出同一段录音的转写，对着比谁更准。

Paraformer 有个差别要单独处理：它原生输出没有标点。整段汉字连成一片，没法直接读。解法是再挂一个 CT-Transformer 标点模型，同样是 int8，对拼接后的全文补标点。一段录音过两道模型，第一道出字，第二道出可读性。

为什么要费劲做 A/B：课堂录音的特点是环境吵、有粉笔声、老师会走到讲台远处，不同模型在这种音频上的差异，跑一遍真录音才知道，看榜单看不出来。对照组容器就是为这个准备的。

## 这节课是谁的课

转写完的文本要归档，归到哪门课？第一层判断靠课表：按收到录音的时刻查日程，正在上的课优先；没有正在上的课，就取前后两小时窗口里最近的一节；日程里什么都没有，进兜底目录「课堂录音」。

```rust
pub fn course_at(&self, received_at: i64) -> String {
    let window = 2 * 3600;
    let service = ScheduleService::new(self.store.clone(), self.options);
    let Ok(occurrences) =
        service.occurrences_between(received_at - window, received_at + window, 20)
    else {
        return self.config.fallback_course.clone();
    };
    let containing = occurrences
        .iter()
        .find(|o| o.starts_at <= received_at && received_at < o.ends_at);
    let nearest = occurrences.iter().min_by_key(|o| (received_at - o.starts_at).abs());
    containing
        .or(nearest)
        .map(|o| sanitize_name(&o.title))
        .filter(|s| !s.is_empty())
        .unwrap_or_else(|| self.config.fallback_course.clone())
}
```

课表可能错。调课、错位、上午的录音下午才想起来发，都会让时刻匹配给出错误答案。所以第二层判断放在整理环节：整理笔记的 agent 拿到课表猜测的课名后，第一件事是读转写内容判断实际是哪门课，再对照 Vault 里现有的课程目录名做校验，明显不符就改判，并在汇报里说明。这里吃过一次亏：同一门高数，课表里的短名和 Vault 里的目录名（带「I(理)」和学期后缀）对不上，笔记被拆进了两个目录。修法就一句：以现有目录名为准，不要自造新名字。

## 笔记的形态：一门课一份文件

形态设计来回改过三次。最早的版本一节课一个文件，转写和笔记都归档，一个学期下来每门课几十个文件。后来想清楚了两件事。

第一，转写和原始音频都是临时产物。原始录音手机里还有，转写的价值在整理后的笔记里已经兑现完了，留在 Vault 里只占地方。所以现在的流程是转写全量内联进 agent 的提示词，不落盘，处理完成后工作目录（原始文件加切片）立即删除。一节课几十 MB 的中间产物，不删的话一学期吃掉十几个 GB。

第二，笔记要按学期连续。每门课只有一份 `课堂笔记.md`，每次课整理完，按「日期 主题」的章节追加在文件末尾，已有内容一字不动。章节顺序就是时间线，复习时从头读到尾，正好是这门课的推进过程。三次重构提交，删掉的文件比留下来的多。

## 整理提示词：为捞分而写

整理环节的提示词是整个管线里最像「产品需求文档」的部分，因为它的用途被限定得死死的：期末复习拿分。围绕这个目标调研了课堂笔记该有什么，最后定下来的栏目按优先级排：

- 题型与方法：本课出现的题型归纳成「题型 → 方法」短条目，复习最先看的部分
- 考试线索：老师关于考试的原话——「会考」「出大题」「分值」，以及「这部分不考」这类排除信息（排除信息同样省时间），每条注明是原话还是推断
- 易错点：老师点名的常见错误，一句话说清错误做法与正确做法
- 例题与讲解（理科课）：逐题记题目、解法步骤、易错点
- 复习清单：每条对应本课出现过的具体题目，可执行可勾选

配套两条硬规则。一是宁缺毋滥：教科书上本来就有的通用定义，只有老师当场强调才记并注明；口语冗余直接舍弃；没有实质内容的栏目整个省略，不留空标题。二是不臆想：只依据转写原文整理，课堂没讲的不补充，破碎片段如实标「待核对」，不编顺滑的假内容；整段转写如果是静音产生的幻觉文本，只写一行说明该段无可整理。转写模型会偶尔在静音段吐出字幕署名之类的东西，这条规则就是给它们准备的。

文科课另有一套：思修、五史这类没有例题的课，把要点整理成问答对，考前盖住答案自测，比读笔记提纲管用。

## 数学听不懂，提示词来兜

一个现实问题：老师讲「根号二乘 x 除以二」，识别模型能不能听懂？

答案是分两层。识别层听不懂「根号」这种口语数学，转出来就是这三个字。所以兜底的活儿交给提示词层：口语数学表达转规范记号，「根号二」转成 $\sqrt{2}$，「x的平方」转成 $x^2$，分式、积分、极限用 LaTeX 写，Obsidian 直接渲染。同音误听也在这一层修——「极限」和「基线」这类，按上下文判断。

这套设计的出发点是承认 ASR 会错，而不是指望换一个永不犯错的模型。识别层负责把声音变成大致正确的字，理解层负责把大致正确的字变成准确的数学。两层各干各的，哪层出问题修哪层。

## 插件深水区：TLS 跨不过 .so 边界

工程上还有一个花絮值得记。机器人是插件化架构，课堂录音整条管线跑在一个 cdylib 插件里。插件和宿主进程共享进程空间，但各自带着一份 tokio 运行时副本，一开始网络请求写在宿主的运行时上，偶发崩在 TLS 握手，排查后发现原因：宿主运行时的 TLS reactor 跨不过动态库边界，插件里的网络 I/O 必须跑在插件自己的运行时里。管线里两处网络调用（下载录音、请求 ASR）现在都套着一层桥接，把异步任务显式投回插件的运行时。

这类问题搜不到现成答案，错误信息也不指向真正的病因。记下来的价值大于解决本身：下次再见到「插件里 TLS 偶发崩」，第一反应应该是查运行时归属。

## 收尾：一学期的成本账

管线现在的形态：QQ 单聊丢录音，当场下载，后台切片转写，按课表和内容双重判断归入课程目录，agent 整理成捞分导向的连续笔记，中间产物即用即删。四套转写方案换下来，最终形态里没有任何一步花钱：识别是本地 int8 模型，整理走的是已有的 agent 额度，存储只留一份每门课的 Markdown。

回头看三次翻车的共性：每次都栽在「假设」上。key 现成是假设，没验证接口权限；官方镜像是假设，没核对硬件约束；临时方案是假设，没设退场时间。管线里剩下的东西，恰好都是把假设换成实测之后的版本——二十四倍实时速度和四百五十 MB 内存，都是这台坏电池笔记本上跑出来的真数字。
