我在宿舍跑着一套自己的助理系统 ru41，之前已经把校园卡小程序拆过一遍，盯住了水电费。这次轮到图书馆。

起因是一件很小的事：我想借 Rust 的入门书，在学校检索系统里查到一本清华大学出版社的《Rust程序设计》，点开馆藏信息，馆藏地写着「某校区样本书库 10（仅供阅览）」。

样本书库的书不外借。书就摆在那里，借不走。

检索系统里没有任何「到货提醒」功能——它压根不认为你会在一本不外借的书上等。于是我自己做了一个：机器人盯住这本书的馆藏状态，哪天它从样本书库搬进普通书库，马上通知我。本文记录的就是这条链路怎么拆开的：登录怎么走、检索接口藏在哪、为什么查「rust 清华大学」永远查不到东西，以及追书功能最后长成了什么样。

先交代边界：整个过程只用了自己的账号，只调了自己有权调的读接口和一次续借；验证码是学校的算术题，本地识别，没有绕过任何风控。

## 点开「个人信息」，我认出了这个登录页

移动图书馆是 `mfind***.libsp.cn`，libsp 是超星旗下的图书馆产品线，全国不少高校用的是同一套。页面是个前端 SPA，点「图书馆个人信息」，跳到了一个登录验证页。

我盯着那个登录页看了几秒——这页我认识。它在教务系统的模块里出现过：联奕 CAS，统一身份认证，`cas.g*.edu.cn/lyuapServer`。图书馆自己不管密码，登录全部转给学校 CAS。

顺着跳转把整条链摸完，画出来是这样：

```
联奕 CAS（统一身份认证，与教务同套）
  └→ 超星统一认证 unified-auth.chaoxing.com
       ├→ mfind***.libsp.cn   移动图书馆（借阅/续借，要登录）
       ├→ find***.libsp.cn    PC 统一检索（后来发现检索不要登录）
       ├→ 学习通 passport2.chaoxing.com（签到/作业，另一套 story）
       └→ reserve.chaoxing.com 空间预约（学校没开通，见「空间预约」一节）
```

一个 CAS，四个业务系统。这就是高校信息系统的现状：界面各找各的设计公司，底下全是同一套认证在撑。好处是逆向了一处，处处能复用——教务模块里写好的算术验证码识别和 RSA 加密，这次原样搬过来就能用。

动手之前先查了社区。libsp 这套产品别的学校也有人拆过：同济站的接入文档把「检索公开、借阅要登录」的边界写得很清楚，GitHub 上各校的找书 bot 走的也是同款接口。外包产品的一个特点是你在 A 校拆明白的东西，到 B 校照样认得。这次调研省了至少一半的试探成本。

## SSO 四跳：jwt 藏在 # 号后面

登录链一共四跳。前三跳和教务一致，第四跳是 libsp 自己的落地，坑就在这一跳。

**第一跳**，libsp 发现前端没有 jwt，跳到超星统一认证的入口：

```
GET https://unified-auth.chaoxing.com/login_auth/v2/g***s/init
    ?refer=https://find***.libsp.cn/find/sso/login/g***s/1
```

返回一个 JS 跳转页，302 链到 CAS 登录页。

**第二跳**，CAS 账密登录。先拿算术验证码：

```
GET https://cas.g*.edu.cn/lyuapServer/kaptcha?uid=<uuid>
→ {"uid": "...", "content": "data:image/png;base64,..."}
```

图上是一道个位数的加减乘法，本地模板匹配就能出答案，准确率实测 40/40。然后提交登录：

```
POST https://cas.g*.edu.cn/lyuapServer/v1/tickets
form: username, password=<Ohdave RSA 密文>,
      service=<超星 service>, loginType=, id=<kaptcha uid>, code=<算术答案>
→ {"tgt": "TGT-..."}
```

这里有两个值得记的细节。密码错返回 `PASSERROR`，响应里的 `data` 字段长这样：`"5,1"`——错 1 次、满 5 次锁号。做自动登录必须见到 PASSERROR 立刻停手，每重试一次都在烧锁号计数。验证码错返回 `CODEFALSE`，不烧密码计数，这个可以重试。

**第三跳**，拿 TGT 换服务票据：

```
POST https://cas.g*.edu.cn/lyuapServer/v1/tickets/<TGT>
form: service=<超星 service>&loginToken=loginToken
→ 响应体就是 ST（ST-...，一次性）
```

**第四跳**，超星验票。拿 ST 访问统一认证，返回 200，但页面不是跳转完成，而是一个「跳转中...」的 HTML，里面埋了三个参数：

```html
var data = "<32位hex>"; var time = "<毫秒时间戳>"; var enc = "<32位大写hex>";
```

抠出来再请求一次，超星侧会话就建好了，然后按 refer 规则跳回 libsp 的落地地址。抠参数的代码五行：

```rust
fn extract_sso_params(html: &str) -> Option<(String, String, String)> {
    let grab = |name: &str| -> Option<String> {
        let re = Regex::new(&format!(r#"var\s+{name}\s*=\s*"([^"]+)""#)).ok()?;
        Some(re.captures(html)?.get(1)?.as_str().to_owned())
    };
    let data = grab("data")?;
    let time = grab("time")?;
    let enc = grab("enc")?;
    Some((data, time, enc))
}
```

最后 libsp 落地，302 到：

```
https://mfind***.libsp.cn/#/Home?jwt=<JWT>&jwtHeader=jwtOpacAuth
```

坑来了。jwt 在 `#` 号后面——URL fragment 里。HTTP 客户端的自动重定向跟随会把 fragment 剥掉，因为 HTTP 规范里 fragment 根本不会随请求发送。也就是说，你让 reqwest 自动跟完这趟 302，`response.url()` 里永远没有 jwt。11 月 1 号在生产上实打实踩了这一脚，最后改成不跟随重定向，手动逐跳读 `Location` 头：

```rust
// 必须手动逐跳跟随：jwt 在 302 Location 的 `#/Home?jwt=...` 片段里，
// reqwest 自动重定向会剥掉 fragment（fragments 不随请求发送），
// response.url() 永远拿不到 jwt。
let mut current = format!("{}/find/sso/login/g***s/1?data={}&time={}&enc={}",
    self.find_base, data.as_str(), time.as_str(), enc.as_str());
let mut hop = 0;
let response = loop {
    hop += 1;
    let resp = self.http_noredir.get(&current).send().await?;
    let status = resp.status();
    let location = resp.headers().get(reqwest::header::LOCATION)
        .and_then(|v| v.to_str().ok()).map(str::to_owned);
    match location {
        Some(next) if status.is_redirection() && hop < 6 => {
            current = if next.starts_with("http") {
                next
            } else {
                format!("{}{next}", self.find_base)
            };
        }
        _ => break resp,
    }
};
```

落地 URL 整体扫一遍，jwt 和鉴权头名一起拿：

```rust
/// 从落地 URL 字符串提取 jwt 与鉴权头名（jwt 在 fragment 里也无所谓，整体扫描）。
fn extract_jwt(final_url: &str) -> Option<(String, String)> {
    let grab = |name: &str| -> Option<String> {
        let start = final_url.find(&format!("{name}="))? + name.len() + 1;
        let rest = &final_url[start..];
        let end = rest.find(['&', '#']).unwrap_or(rest.len());
        let value = &rest[..end];
        (!value.is_empty()).then(|| value.to_owned())
    };
    let jwt = grab("jwt")?;
    let header = grab("jwtHeader").unwrap_or_else(|| "jwtOpacAuth".into());
    Some((jwt, header))
}
```

注意 `jwtHeader` 也是从 URL 里读出来的。鉴权头的名字不是写死的，校方或超星哪天换个名字，客户端跟着变就行，不用改代码。jwt 的 payload 里有 `sub`、`groupCode`、`mappingPath`，有效期 24 小时。

## 借阅接口：三个头，三个必填字段

登录完，业务接口全在 `mfind***.libsp.cn` 同源下，POST JSON，每个请求带三个头：

| 头 | 值 | 说明 |
|---|---|---|
| `jwtOpacAuth`（名字从 jwtHeader 参数读） | `<JWT>` | 鉴权 |
| `groupCode` | `2*****0` | 学校编码，jwt 里也有 |
| `mappingPath` | 空字符串 | 移动端 SPA 固定空串 |

缺鉴权头会得到一个仪式感很足的报错：

```json
{"success":false,"message":"系统访问中断，请稍后再试！","errCode":9999,"errorCode":null,"data":null}
```

「系统访问中断」其实是「你没带凭证」。比它更麻烦的报错是「参数异常 {0}」——格式对了一个字段名，就得到这句话，不告诉你哪个字段错。

当前借阅接口 `POST /find/loanInfo/loanList`，请求体是前端抓包拿到的：

```json
{"page":1,"rows":20,"searchType":1,"searchContent":"","sortType":0,
 "startDate":null,"endDate":null}
```

实测 `searchType`、`searchContent`、`sortType` 三个字段缺一个都不行，只传分页参数直接「参数异常」。响应里 `loanNum` 是还可借册数，`numFound` 是当前在借数，记录字段里有 `loanDate`（借出）、`normReturnDate`（应还日期）、`locationName`（馆藏地）——催还提醒要的就是 `normReturnDate`：到期前 3 天、1 天、当天各提醒一次，提醒消息上带一个「续借」按钮，点了就是以我的身份调 `POST /find/lendbook/reNew`。

按钮做上去之后第一次点击，QQ 那边回「无权限操作」。查下来是按钮的 permission type 传错了，0 改成 2 就好了。这种坑和图书馆没关系，是消息渠道侧的，但它提醒我插件化之后每个附属都要自己把渠道层的约定过一遍。

## PC 检索站：检索居然不要登录

移动站的接口都要 jwt，我以为检索也一样。后来发现检索系统在 PC 端有独立入口 `find***.libsp.cn`，和移动端是同源产品，但检索类接口完全公开——不要 jwt，不要 cookie，只要两个公开的头：

```
groupCode: 2*****0
mappingPath: g***s        ← 注意 PC 站是这个值，不是空串
```

同一个 `mappingPath` 字段，移动端 SPA 传空串，PC 站传学校代号。这个字段是前端按页面路径生成的，两站路径不同，值就不同。

这里的报错行为值得单独记录，因为三种姿势三种结局，全试出来了：

```
# 什么都不带
→ {"success":false,"message":"系统访问中断，请稍后再试！","errCode":9999}

# 带 jwt 和 groupCode，缺 mappingPath
→ 200，JSON 正常返回，但 numFound 恒为 0

# 带旧登录会话的 SESSION cookie 去请求
→ 401「请登录」
```

第三种最反直觉：带着合法 cookie 去访问免登录接口，反而被拒。第二种最隐蔽——HTTP 200，JSON 结构完好，`success:true`，就是结果永远为空。报错会逼你去查，静默空结果只会让你以为自己关键词没输好。

静默空结果我确实以为过是关键词的问题。最早没有前端 schema，我拿移动端借阅接口的字段名去猜检索接口的请求体：

```
{"searchType":"1","searchContent":"Python","page":1,"rows":5}
→ success:true, numFound:0
```

换 Python 还是 0。Python 的书一个图书馆不可能没有，这说明是请求体的问题。正面强攻查不动，回头啃前端。

libsp 的前端是个 webpack 打包的 SPA：入口壳加载 `manifest`，里面存着 74 个懒加载 chunk 的 `{id: 20位hash}` 映射表，按需拉 `static/js/<id>.<hash>.js`。静态资源带防盗链，请求必须带站域 Referer。把 74 个 chunk 全下下来 grep——服务层定义在 chunk 20，dva/redux 架构，所有接口调用都是 `s.post("/find/...", payload)` 的形式，一行一个端点：

```js
getResourceList: function(e) { return s.post("/find/unify/search", e) },
advanceSearch:  function(e) { return s.post("/find/unify/advancedSearch", e) },
```

检索 payload 的组装在搜索页组件的 chunk 里，对出来真实 schema：

```json
{"searchField":"keyWord","searchFieldContent":"Python","matchMode":"2",
 "page":1,"rows":10,"sortField":"in_date","sortClause":"desc"}
```

和我猜的完全不是一个结构：字段名是 `searchField`/`searchFieldContent`，不是 `searchType`/`searchContent`；还多了 `matchMode`（"2" 是模糊匹配）和排序字段。服务层那一份端点清单顺便把整个 API 面都亮了：书目详情、单册馆藏、热门借阅榜、新书通报、联想词，全在同一个 `getBookDetail`、`groupitems`、`getHotLoan` 这样的命名下。

顺带在 chunk 里看到了一个后来很关键的端点：`getBookCoverImg: s.get("/find/book/getDuxiuImageUrl", e)`。独秀封面。先记下，后文要用。

## 「rust 清华大学」为什么查不到

schema 对了之后，检索通了。然后撞上第二个坑，这个坑直接决定了找书命令的形态。

用户不会按字段输入。他输入的是「rust 清华大学」——想找清华社出的 Rust 书。这两个词拼进 `keyWord` 一查：

```
keyWord「rust 清华大学」       numFound: 0
keyWord「Rust 清华大学出版社」  numFound: 0
keyWord「rust」              numFound: 188
  - Rust语言编程实战 | 中国电力出版社
  - Rust权威指南 | 电子工业出版社
  - 精通Rust | 人民邮电出版社
```

整串文本被当成一个词去匹配，书名、摘要、主题里没有任何一条包含「rust 清华大学」这个连续字符串，于是一条都出不来。真要组合条件，得走高级检索接口 `advancedSearch`，它的请求体长这样：

```json
{"searchItems":[
   {"oper":null,     "searchField":"keyWord",   "matchMode":"2","searchFieldContent":"rust"},
   {"oper":"AND",    "searchField":"publisher", "matchMode":"2","searchFieldContent":"清华大学"}],
 "docCode":[],"page":1,"rows":10,"sortField":"relevance","sortClause":"desc"}
```

首项 `oper` 为 null，后续项填 AND/OR/NOT；`searchField` 可选题名、作者、出版社、索书号、ISBN 等（注意是 camelCase，`keyWord` 不是 `keyword`，写错不报错，静默查不到东西）。这样查，「rust + 清华大学出版社」出 12 条。

所以找书命令里加了一层拆词：识别出哪个词像出版社，自动拆成组合检索：

```rust
pub fn build_search_items(query: &str) -> Vec<SearchItem> {
    const PUBLISHER_HINTS: &[&str] = &[
        "出版社", "出版集团", "出版传媒", "书局", "书社", "印书馆", "大学",
    ];
    let tokens: Vec<&str> = query.split_whitespace().collect();
    if tokens.len() < 2 {
        return Vec::new();
    }
    let mut items = Vec::new();
    for token in tokens {
        let is_publisher = PUBLISHER_HINTS.iter().any(|h| token.contains(h));
        items.push(SearchItem {
            oper: if items.is_empty() {
                None
            } else {
                Some("AND".to_owned())
            },
            search_field: if is_publisher { "publisher" } else { "keyWord" }.to_owned(),
            content: token.to_owned(),
        });
    }
    items
}
```

词表法不聪明，但对中文出版社的识别够用——名字里带「出版社」「书局」「大学」的基本就是它。拆完还会把拆词结果回显给用户：「关键词『rust』＋出版社『清华大学』」，让人知道机器人是怎么理解这句话的。

第三个坑是样本书库。馆藏单册接口 `groupitems` 返回每一条单册的馆藏地、索书号、在架状态。问题在于，样本书库的单册和普通书库的单册，除了 `locationName` 文字，其他字段一模一样——`processType` 照样是「在架」，单册策略照样是普通。也就是说你想按「可否外借」过滤，接口层面没有任何标志位，只能看馆藏地名字里有没有「样本」：

```rust
impl HoldingItem {
    /// 是否可借（在架）。
    pub fn is_on_shelf(&self) -> bool {
        self.process_type.as_deref() == Some("在架")
    }

    /// 样本库单册：仅供馆内阅览，不外借（字段与普通馆藏一致，
    /// 只能靠馆藏地名字识别，如「某校区样本书库」）。
    pub fn is_sample(&self) -> bool {
        self.location_name
            .as_deref()
            .is_some_and(|l| l.contains("样本"))
    }

    /// 借出单册的应还日期（processType 形如「借出-应还日期:2026-11-22」）。
    pub fn due_back(&self) -> Option<String> {
        let raw = self.process_type.as_deref()?;
        raw.strip_prefix("借出-应还日期:")
            .map(str::trim)
            .filter(|s| !s.is_empty())
            .map(str::to_owned)
    }
}
```

`due_back` 顺带解释了另一种状态的表达方式：借出去的书，`processType` 不是状态词，是「借出-应还日期:2026-11-22」这样一整串拼起来的字段。应还日期就拼在里面，取的时候按前缀剥。

馆藏地我把实测到的列一下：社科书库、自科书库、计算机书库、文学书库、密集书库、过刊库、网络系资料室、某校区样本书库、某校区复本库、异地分馆、分馆计算机书库、分馆综合书库、分馆复本库。其中「复本库」实测可以借出，不算样本——名字里带「库」的地方，规则并不统一，每个都得真借一次（或者看别人借过）才知道。

## 找书命令的三轮打磨

接口通了之后，`/找书` 命令打磨了三轮，每轮都是用了两天后被反馈戳出来的。

**第一轮：没有馆藏的书要不要显示。** 检索是书目级的，一条书目下面可以挂零条单册馆藏——书目录里订了，馆里实际一本没有。初版老老实实全列出来，结果一半的条目是「查得到、借不到」的空欢喜。改法分三步走的：无单册馆藏的书目整条隐藏；隐藏的书目也不出现在推送里；并且拒绝被追书——追一本馆里从来没有过、也看不出会有的书，追踪本身没有意义。

**第二轮：封面。** 第一版的找书结果是纯文字卡片，反馈是「书需要图片」「markdown 里面本身就可以塞图片」。回头看，线索其实在拆检索站那节就埋下了：chunk 里有 `getBookCoverImg` 端点（独秀，读秀的图床）。但最早那批检索结果里每本书的 `pic` 字段都是 `None`，封面并不随检索结果下发，得单独去取。中间还走过一段弯路：封面图单独发了一条消息，反馈是「你单独给我发啥意思」——图和条目分离就没有可读性了。最后的形态是 QQ 命令回复支持原生图片消息，封面字节下载下来直接嵌进结果卡片：

```
《Rust权威指南》
Steve Klabnik, Carol Nichols｜电子工业出版社｜2020｜索书号 TP312/1333
 ↳ 可借 2 册｜计算机书库 在架2/2
```

每本书带图、带架位（馆藏地＋索书号，到书库按索书号升序找架，同号段相邻）、带可借册数。

**第三轮：追书。** 最初版追书按 recordId 追——追的是那一条具体书目记录。问题是同一本书在系统里可能有多条记录（不同印次、不同册次各一条），追了 A 记录，B 记录进书库了你也不知道。后来改成书名级追踪：追「这本书」，而不是「这条记录」。实现上是追书任务到期时，先看 pinned 那条记录的可借数，仍是 0 的话拿书名（和已知的出版社）回检索一遍，同名其他记录里有可借的就通知，每个替代版本只报一次。

而「可借」的判定，最后收敛成一行：

```rust
.filter(|h| h.is_on_shelf() && !h.is_sample())
```

在架，且不是样本。检索那节里三个坑，全部收在这一个谓词里。

还有一条收窄：只接受「暂不可借」的书进入追书——样本书库的、全部借出的可以追；馆藏为零的不收。一开始没这个限制，追书列表里混进了几本馆里压根没有的书，每次检查都是白跑。

## 空间预约：查了个寂寞，但查明白了

移动图书馆的菜单里有个「空间预约」，点进去跳到 `reserve.chaoxing.com`，页面报 500，附一句「该应用只允许本单位用户使用」。

这句话有两种可能的解释：登录链没打通，或者学校压根没开通这个应用。值得花一个探针脚本分清楚。

探针走了一遍完整链路，重点验证的是**会话能不能从统一认证迁到超星主域**：拿 unified-auth 的 cookie 访问 `passport2.chaoxing.com/wlogin`，一次跳转拿到 `.chaoxing.com` 域的全套 cookie（`_uid`、`fid`、`vc3`、`p_auth_token`），再访问超星个人空间 `i.chaoxing.com`，200，是真登录态。本校在超星侧的 fid 和 libsp 的 groupCode 是两套编号，记下来备用。

然后带着这个真实会话去访问 `reserve.chaoxing.com` 的全部路径——404，全部 404。学习通 App 里点同一个入口，报的还是那句话。

结论：登录链没有任何问题，是学校没有购买开通超星的空间预约应用。探索的产出是「不可做」的证明，外加一条存着的会话迁移链——哪天学校开通了，接入是从头到尾现成的。

## 收尾

现在的状态：QQ 里发 `/找书 rust`，十秒出头，回来一组带封面、带架位、带可借册数的卡片；借的书到期前三天机器人开始催，消息上带续借按钮；样本书库那本《Rust程序设计》在追书列表里，它哪天搬进普通书库，我会第一个知道。

最后记三条这次拆下来的经验，给同样想拆学校系统的人：

- 外包系统先查社区再动手。全国高校用的就那么几套外包产品，libsp、正方、强智、联奕，你面对的接口大概率有别校学生已经拆过，同济站的文档这次直接省了一半时间。
- 「公开」和「免登录」要分清楚。PC 检索站所有接口都不验证身份，但你要是把别处拿来的 cookie 带上，它反而拒你——每个接口的鉴权约定是独立的，别用已有会话去套。
- 返回 200 但结果为空，比报错难调十倍。遇到静默空结果，尽早回头啃前端 chunk，请求体的真相在打包后的 JS 里，不在你的猜测里。

那本借不了的书什么时候能借，我不知道。但至少现在，有东西替我盯着了。
