# 把主力机换成 Omarchy 的这四天

几天前那篇[《一切透明的都在卡》](/2026/10/26/2026-10-27-一切透明的都在卡-我的gnome卡顿批判书-以及我对omarchy的期待/)的结尾，我是这么写的：

> 计划是这样的：虚拟机里先跑满一个月……如果帧率真的如传闻中那样"动画如丝、待机零烧"，就找个周末给这块 4K 屏一个重新做人的机会。

计划很稳重。实际发生的事情是：批判书 10 月 27 日深夜发布，第二天我开始写备份方案，10 月 28 日主力机重装完毕：Omarchy 4.0.6，Hyprland 0.57，裸机启动到桌面比之前 GNOME 冷启动 gnome-shell 还快。

帧率问题，兑现了。批判书里的三宗罪，兑现了两条半。代价是后面六个坑。

## 重装前的备份

重装系统这件事，技术含量最低的部分是装系统本身，真正要命的是装之前的备份。

我在备份清单上花了整整一个晚上，最后的结论可能和大多数人不一样：这台机器上最值钱的资产不是代码仓库。代码都在远端，`git clone` 一遍就回来了。最值钱的是各个 agent 的状态。

这台机器常年跑着好几个 AI agent：个人助理的课表和日程数据库、各家 coding agent 的会话历史、项目里的 agent 配置和技能库。这些东西的共同点是：不在 git 里、不可再生、丢了就是真丢了。课表同步数据库是靠 school SSO 认证一点一点落库的，会话历史是几百次上下文累计出来的，agent 配置是反复调教出来的。备份方案最终落成三层：

1. 家目录全量 rsync 到外置盘，排除明显的垃圾目录（`node_modules`、各种 cache）。这一层保底。
2. "不可再生"专项清单：agent 数据库、会话目录、SSH/GPG 密钥、浏览器 profile、Thunderbird profile、crontab、`~/.local/src` 下所有手工项目。这一层单独校验了文件数和大小。
3. 重装后按清单逐项归位，而不是无脑 rsync 回去，因为 Omarchy 的家目录骨架和 Ubuntu 不一样，无脑覆盖会把发行版的好意覆盖掉。

事后看，第 2 层救了我一次：某个 agent 的数据库在第一层的排除规则里被误伤（路径里带着 `cache` 字样），靠专项清单才捞回来。凡是按模式排除的规则，都要假设它会误伤一次。

## 批判书兑现了吗

批判书列了三条罪状，装完系统逐条对账。

取舍权这条，兑现。批判书里我最恨的是 GNOME 没有"总闸"，逼用户在"卡顿的浪漫"和"裸奔的朴素"之间二选一。Omarchy 这边所有视觉效果 opt-in，主题、透明度、动画都有开关，而且这些开关是真的开关，后面讲的 mac 化改造（玻璃顶栏、恒定深色终端、假熄屏）全部建立在这套"可关"的地基上。

默认体验这条，也兑现。这台机器的显示器是一块 HDMI 2560x1440，我想要 1.3 倍缩放。GNOME 时代这是一个下拉菜单加一次全员重排；Omarchy 这里是 Lua 配置里的两行：

```lua
local omarchy_monitor_scale = 1.3
hl.monitor({ output = "", mode = "preferred", position = "auto", scale = omarchy_monitor_scale })
```

改完重载，即时生效，没有任何应用集体抽搐。批判书里许的愿"自己写一行就解决，而不是无处可写"，字面意义上实现了。

私有复杂度这条，兑现一半。说兑现，是因为这四天改的东西全是人类可读的：Lua 配置、shell 脚本、Python 插件、一个 Rust 小工具，没有一个改动需要碰编译型的 shell 源码，对比当年给 gnome-shell 打 JS 补丁还要留 rollback.sh 的日子，轻松了不止一档。说一半，是因为私有复杂度并没有消失，只是换了形状：它从 gnome-shell 的 JS 内部，转移到了 quickshell 插件生态的边界上。下面六个坑里，有两个的根源是"官方插件没想到有人这么用"。

## 六个坑

下面这部分是正文。这六个坑没有一个能在搜索引擎里直接搜到答案，全靠读源码。如果你也在用 Omarchy 4.x + Hyprland 0.57 的 Lua 配置，大概率会撞上其中几个。

### 浏览器永远沉底

浏览器窗口永远被压在工作区最底层，新弹出的浮窗直接盖在它脸上。我给浏览器写了 `float = true` 的规则，无效；改成别的规则，也无效。

翻 Omarchy 自带的 `apps/browser.lua` 才找到原因：官方给所有 chromium 系浏览器打了一个 tag（大意是 "chromium-based-browser"），规则内容是强制 `tile = true`——官方认定浏览器就该平铺，为的是配合它的 webapp 体系。问题在于 Hyprland Lua 这套窗口规则里，带 tag 的规则求值顺序晚于普通规则。也就是说，不管我在自己的配置里写多少条 `float = true`，都会被那条 tag 规则在更晚的时机覆盖回去。我写的不是规则，是许愿。

打不过就加入，用同一个 tag 通道写覆盖规则：

```lua
o.window({ tag = "chromium-based-browser" }, { float = true, ... })
```

同样的 tag、同样的通道、放在更靠后的位置，float 就生效了。

这条不算 bug，算设计取向，官方就是想让浏览器平铺。但"用户写了 float 规则却被无声覆盖、且文档里找不到 tag 求值顺序说明"这件事值得一条文档 issue，待我整理。

### dock 会把我的抽屉掏空

我用 Hyprland 的 special workspace 做了一个"抽屉"：按 `Super+S` 呼出一个收藏应用抽屉，塞几个常驻但不想占工作区的东西。用起来发现一个灵异现象：只要在 dock 上点击任何应用，抽屉里的窗口就会被拽出来丢到当前工作区。

读 dock 插件的 `dock-minimize.py`，真相是它把所有 special workspace 都当成了自己的"最小化仓库"：最小化逻辑是"窗口塞进 special 工作区"，恢复逻辑是"从 special 工作区搬出来"。它不知道 special 工作区除了官方的最小化语义之外，还可以被用户拿来当抽屉用。我塞在抽屉里的窗口，在它眼里全是"被你最小化的窗口"，点 dock 自然全部释放。

修法是给 `dock-minimize.py` 打补丁，加一个 `reveal_user_drawer()` 函数：释放窗口之前先检查目标是不是用户自建的抽屉工作区（按命名区分），是就跳过。备份留在 `.bak-drawer`。

读源码时还捞到一条鱼：插件有一个更隐蔽的 bug，`toggle_special` 的调用把参数装进 dict 传递，插件端却按位置参数接收，多余参数被 Python 静默丢弃，结果它每次都开了一个空名字的默认 special 工作区，和用户的抽屉并行存在。不报错、不警告、不留痕迹，只在行为上留下一个"怎么多了个空抽屉"的疑问。这种静默失败花掉了我最多的调试时间。

这条值得上游讨论：抽屉是 Hyprland 用户的常见玩法，dock 插件不该独占 special workspace。

### 锁屏后壁纸全黑

这是四天里最诡异的 bug，也是修得最满意的一个。

Omarchy 的锁屏在 5 秒后会触发 DPMS 真熄屏。我离开座位回来敲键盘唤醒，锁屏界面出来了，背后的壁纸却没了，整个桌面只剩应用窗口浮在纯黑上。重新设壁纸没用，重启 quickshell 才恢复。

在 quickshell 里复现出了链条：DPMS 熄屏再唤醒，会导致 quickshell 的某个层重建，重建后的壁纸层 alpha 值卡死在 0。已经提交 issue（omacom/omarchy#12554），附了复现路径。

等上游是等不起的，何况我本来就想要一个"假熄屏"：锁屏后屏幕黑掉，但不是 DPMS 断信号，而是背光意义上的黑，这样唤醒链路完全不经过那个出 bug 的重建路径。做法是改 `/usr/bin/omarchy-brightness-display`，用 `wl-gammarelay-rs` 把 gamma 压到 0（软件意义上的全黑，信号还活着），并把原亮度值写进状态文件 `$XDG_RUNTIME_DIR/omarchy-fake-blank.brightness`；唤醒时锁屏监听输入事件、走 `omarchy-system-wake`、按状态文件恢复 gamma。整条链路没有任何 DPMS 参与，那个重建 bug 从根上被绕开了。

熄屏黑壁纸的 issue 等上游；假熄屏是我留在本地的方案，上游修了再决定去留。每个本地补丁都应该有一个退役计划。

### Alt+Tab 只在当前工作区循环

单窗口工作区里按 Alt+Tab，毫无反应。默认绑定的 `cycle_next` 语义是当前工作区内循环，而全局 Alt+Tab 是肌肉记忆，我在哪个工作区都习惯性按它。麻烦在于"全局按创建顺序循环窗口"这件事，Hyprland 的 dispatch 层面没有现成原语。

这种小工具轮到 Rust 出场：`~/.local/src/alt-tab-global/`，核心逻辑不到两百行，通过 Hyprland 的 socket 拿全窗口列表，按窗口创建顺序排序，维护一个循环指针，`serde_json` 处理 IPC 消息。编译产物丢进 `~/.local/bin`，绑定改一行，Alt+Tab 从此全局。Rust 在这种场景下舒服的地方是写完扔那儿，永远不会因为某次依赖升级在某个深夜崩给我看。

这不算 bug，是语义选择，官方大概认为工作区内循环更符合 tiling 习惯。我的看法：给个选项，别替我选。

### 自动昼夜主题

Omarchy 自带昼夜主题定时切换（7:00 / 19:00 各一次），听起来很美好，实际启用后我的一天是这样度过的：早上顶栏变纯白，晚上终端跟着主题变浅色，dock 边框颜色和壁纸脱节。一个"自动美化"功能制造了三种不协调。

把问题拆开是三条线。壳层：顶栏和 dock 的颜色来自主题文件，覆盖入口在用户级的 `~/.config/omarchy/shell.toml` 和 `shell.json`，而且两个开关都要动（`background-alpha` 和 `bar.transparent`），只改一个会出现"半白半透"的中间态。dock：它会自动跟随主题里的 `Color.bar.background`，改了壳层它自己跟，这条线不用管。终端：主题一切换，foot 的配色跟着换，浅色主题下终端变白——但我不想要会变色的终端，终端就该恒定深色。

三条线各修各的。壳层用 `shell.toml` 覆盖层固定玻璃顶栏（`background-alpha = 0.75`）。终端走双保险：`foot.ini` 的 include 直接指向恒定的 mocha 深色配色文件，同时放一个主题钩子 `theme-set.d/foot-pin-dark.sh`（挂在官方的 `theme-set.d` 目录里），每次主题切换之后用 OSC 序列把深色重推给所有已经开着的终端。为什么要双保险？配色文件只管新开的终端，OSC 重推只管已经开着的，两条路径各管一半，缺一就会出现"新开的是深色、旧窗口还是白色"的精分现场。

这条不上游，是"官方给的自动切换"和"用户想要恒定深色"之间的偏好冲突，覆盖层和钩子机制本来就是为这种场景准备的。Omarchy 在这一点上的可定制性是对的。

### 无头安装 Windows VM

Omarchy 内置了 `omarchy-windows-vm`，一等公民，底层是 dockur/windows 容器 + KVM，装完 FreeRDP 直连 3389 端口，还有个 8006 的网页控制台。但它的安装器是纯 TUI 交互：`gum choose` 弹菜单问你内存给多少、CPU 给几核，`sudo` 要 TTY 提密码。而我是从 SSH 会话里远程操作的，没有 TTY，交互到第一步就死。

不想改官方脚本（升级会被冲掉），就在 PATH 前面垫一层 shim：假的 `gum`，对 `choose`/`input`/`confirm` 按预设答案作答（8G 内存、4 核、128G 磁盘，confirm 一律 yes）；假的 `sudo`，转发成 `sudo -A`，askpass 指向一个 zenity 弹窗，密码由人来输，垫片本身永远不经手密码。

垫片就位后整个安装一路无头跑通，容器 `omarchy-windows` 起来后 Windows 在容器内自己装自己，RDP 连上去就是成品桌面。这套垫片留在 `~/.local/src/win-vm-headless/shims/`，下次有同类 TUI 安装器要自动化，换个答案表就能复用。

给安装器加 `--headless` / 答案文件支持是合理的 feature request，待提。TUI 安装器对人类友好，对自动化零友好。

## 一些想法

webapp 是一等公民，这不是段子。装完系统数了一下，`~/.local/share/applications` 里的 `.desktop` 文件，一半以上是 `chromium --app=...` 的套壳——WhatsApp、Notion、各种 SaaS 都是这么"装"的。第一次看到会觉得寒酸，用几天就理解了：对 DHH 来说，浏览器就是运行时，为每个 SaaS 维护原生客户端是重复建设。代价是这些 webapp 的窗口规则要逐个调（见「浏览器永远沉底」一节），收益是"装一个应用"的成本趋近于零。

没有桌面图标不是阉割，是立场。我一开始也不习惯，文件往桌面一放的条件反射戒不掉。后来想明白了：桌面文件的本质是"用空间位置管理文件"，这在 tiling 工作流里是异类——工作区是时间维度（切换），桌面文件是空间维度（摆放）。Omarchy 选了工作区，补偿方案是绑定到文件管理器的一键直达。想通了就是解放，想不通就难受着。

"opinionated"的账要算两遍。收益是默认值处处可用，这四天里的多数不满其实是在"改默认值"而不是"修 bug"。成本是当你的用法撞上官方预设——抽屉用户撞上 dock 的最小化假设，恒定深色党撞上自动换肤——没有设置项给你，只有源码给你。所以我的用法是把 Omarchy 当一份写得很好的开源桌面参考实现，而不是当产品：产品出问题只能等补丁，参考实现出问题直接改，反正它就是一堆可读的 Lua 和脚本。

## 现状

回到批判书的中心思想，给这四天验收：

- "GNOME 给了我一切，唯独没给我帧率"——帧率还了。工作区切换、窗口动画、Overview 级别的操作全部满帧，待机时 CPU 归零，"an idle desktop stops burning CPU" 不是营销话术。
- "我要的是一个一切皆可关的桌面"——给了，而且给了工具。覆盖层、钩子目录、Lua 配置，"可关"之上还有"可改"。
- 批判书没预料到的是：可改的桌面会把用户变成贡献者。四天里我提交了一条 issue、计划再提三条、打了两份本地补丁、写了一个 Rust 工具。不是我勤奋，是这套系统改起来的阻力足够低，低到顺手就修了。

遗留问题立此存照：锁屏壁纸那条 issue 等上游；顶栏歌词插件不渲染的问题（第三方 lyrics 插件）挂在 issue 区等作者；两份文档类 issue 待整理提交；4K 那台笔记本还没迁，它的分数缩放 + HiDPI 组合是 Hyprland 的另一场硬仗，等打完再说。

至于 GNOME，告别的话在批判书里已经说完了，就没有再联系的必要了。
