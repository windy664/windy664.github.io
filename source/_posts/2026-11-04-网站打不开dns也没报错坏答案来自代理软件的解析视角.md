家里那台 PC 上，某个国内网站的某个页面怎么点都转不出来，浏览器一直转圈直到超时。DNS 没有报错，TLS 也没有报错，ping 目标 IP 甚至零丢包。最后查下来，问题既不在网站，也不在宽带，而是代理软件 mihomo 接管内网 DNS 后给出的解析视角，把这次访问派到了一台当时从家里连不上的 CDN 边缘节点。

<!-- more -->

## 现象：报错不在 DNS，也不在 TLS，卡在 TCP 握手

第一步是把「错在哪一步」缩小到具体阶段。PC 上没装 nslookup，能用的信号只有 curl 的详细输出：

```bash
echo '--- DNS ---'; nslookup www.example-site.cn 2>&1 | tail -6; echo '--- PC curl ---'; curl -sv -o /dev/null --interface wlp2s0 --max-time 15 https://www.example-site.cn/index/User/user.html 2>&1 | grep -E 'Trying|Connected|HTTP/|SSL|error|timed|refused|reset' | head -12
```

```
--- DNS ---
/bin/bash: 行 1: nslookup: 未找到命令
--- PC curl ---
*   Trying 198.51.100.10:443...
* Connection timed out after 15001 milliseconds
```

这两行把阶段划得很清楚。`Trying` 后面跟着 IP，说明域名已经解析成功，解析阶段没报错；连接停在 15 秒超时，而且整个输出里没有任何 TLS 相关报错，说明三次握手根本没完成，后面连证书和 HTTP 都没走到。问题因此很具体：DNS 给的这台 IP，从我这台机器连不上。

## 排除法：不是断网，也不是这台 PC 的问题

接下来排除「家里断网」和「这台 PC 自己有毛病」两种可能。路由器是 OpenWrt，先看它的多拨状态：

```bash
sshpass -p '<口令>' ssh root@192.168.1.1 'echo "--- mwan3 status ---"; mwan3 status 2>/dev/null | grep -E "wan[0-9]*|online|offline" | head -20; echo "--- route get (from PC) ---"; ip route get 198.51.100.10 from 192.168.1.125; echo "--- router direct curl ---"; curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" --max-time 10 https://www.example-site.cn/ '
```

```
--- mwan3 status ---
 interface wan is online and tracking is active (online 00h:46m:53s, uptime 274h:42m:22s)
 interface wan2 is offline and tracking is active (16)
 interface wan4 is online and tracking is active (online 00h:26m:37s, uptime 00h:44:08s)
 wan4 (50%)
 wan (50%)
--- route get (from PC) ---
--- router direct curl ---
RTNETLINK answers: Network unreachable
ash: curl: not found
```

`wan` 和 `wan4` 都是 online，宽带侧没问题。`ip route get ... from 192.168.1.125` 报 Network unreachable 看着吓人，但这台路由器用 `ip rule` 加 fwmark 分流，没有按源地址选路的路由表，这种命令在这里本来就可能返回 unreachable，不能拿来判断可达性。路由器上也没装 curl，这条路走不下去。

于是换到代理机，用它自己的出口直连同一个 URL：

```bash
sshpass -p '<口令>' ssh windy2@192.168.1.244 'curl -s -o /dev/null -w "windy2 direct: %{http_code} %{time_total}s\n" --max-time 12 https://www.example-site.cn/index/User/user.html'
```

```
windy2 direct: 000 12.002941s
```

代理机直连同样是 `000` 超时，走的是它自己的出口，和 PC 无关。这下问题既不在 PC，也不在这台机器的代理规则上，而在「DNS 给的那台 IP，从家里这条线路连不上」。

## 同一时刻，三路 DNS 给出三个 A 记录

关键一步是把「DNS 到底给了什么」摊开来看。在代理机上并排问两路：

```bash
sshpass -p '<口令>' ssh windy2@192.168.1.244 'echo "--- 223.5.5.5 (ali) ---"; dig +short @223.5.5.5 www.example-site.cn A 2>/dev/null || getent hosts www.example-site.cn; echo "--- mihomo dns(1053) ---"; dig +short @127.0.0.1 -p 1053 www.example-site.cn A; echo "--- ping resolved ip ---"; ping -c 3 -W 2 198.51.100.10 | tail -3'
```

```
--- 223.5.5.5 (ali) ---
www.example-site.cn.w.example-cdn-gslb.com.
198.51.100.20
--- mihomo dns(1053) ---
www.example-site.cn.w.example-cdn-gslb.com.
198.51.100.10
--- ping resolved ip ---
--- 198.51.100.10 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 22.529/22.856/23.051/0.232 ms
```

两条答案的 CNAME 完全一样，都指向 `www.example-site.cn.w.example-cdn-gslb.com`，说明背后是同一套 GSLB 调度；不一样的只有最后那行 A 记录。GSLB 是按「谁来问、什么时候问」挑边缘的，同一个域名在不同视角下拿到不同节点，是它的正常行为。

再往细看，mihomo 这条路的答案是稳定的，不是抖动：

```bash
sshpass -p '<口令>' ssh windy2@192.168.1.244 'for i in 1 2 3; do dig +short @127.0.0.1 -p 1053 www.example-site.cn A | tail -1; done; echo "--- doh.pub direct ---"; curl -s "https://doh.pub/dns-query?name=www.example-site.cn&type=A" -H "accept: application/dns-json" | head -c 400; echo; echo "--- alidns direct ---"; curl -s "https://dns.alidns.com/resolve?name=www.example-site.cn&type=A" | head -c 400'
```

```
198.51.100.10
198.51.100.10
198.51.100.10
--- doh.pub direct ---
{"Status":0,"TC":false,"RD":true,"RA":true,"AD":false,"CD":false,"Question":[{"name":"www.example-site.cn.","type":1}],"Answer":[{"name":"www.example-site.cn.","type":5,"TTL":600,"data":"www.example-site.cn.w.example-cdn-gslb.com."},{"name":"www.example-site.cn.w.example-cdn-gslb.com.","type":1,"TTL":60,"data":"198.51.100.40"}]}
--- alidns direct ---
{"Status":0,"TC":false,"RD":true,"RA":true,"AD":false,"CD":false,"Question":{"name":"www.example-site.cn.","type":1},"Answer":[{"name":"www.example-site.cn.","type":5,"TTL":600,"data":"www.example-site.cn.w.example-cdn-gslb.com."},{"name":"www.example-site.cn.w.example-cdn-gslb.com.","type":1,"TTL":60,"data":"198.51.100.40"}]}
```

同一个时刻三路解析给出三个不同的 A：国内 UDP DNS 给 `198.51.100.20`，mihomo 自己给 `198.51.100.10`，直接问 doh.pub 和 alidns 的 DoH 接口两家都给 `198.51.100.40`。

这时最容易犯的错是拿 ping 当结论。`198.51.100.10` 的 ICMP 零丢包、平均 22.856ms，看着非常健康，但 ping 只说明这个 IP 的 ICMP 有回包，跟 443 端口上有没有东西应答完全是两回事。

## 唯一的变量是 IP：curl --resolve 对照实验

要坐实「问题出在 IP 而不是域名」，做一个只改一个变量的对照实验。curl 的 `--resolve` 可以绕过 DNS，把域名强行钉到指定 IP：

```bash
curl -s -o /dev/null -w "ali-ip(198.51.100.20): %{http_code} %{time_total}s\n" --interface wlp2s0 --max-time 12 --resolve www.example-site.cn:443:198.51.100.20 https://www.example-site.cn/index/User/user.html; curl -s -o /dev/null -w "mihomo-ip(198.51.100.10): %{http_code} %{time_total}s\n" --interface wlp2s0 --max-time 12 --resolve www.example-site.cn:443:198.51.100.10 https://www.example-site.cn/index/User/user.html
```

```
ali-ip(198.51.100.20): 302 0.195481s
mihomo-ip(198.51.100.10): 000 12.001738s
```

同一条命令、同一个网卡、同一个 URL、同一个出口，只有目标 IP 不同，结果却是 0.19 秒返回 302 和 12 秒超时。SNI、Host 头、路径、TLS 握手全都一样，说明域名没被污染也没被劫持，域名本身好着呢；路由和出口也没问题，否则好 IP 同样连不上。到这一步，GSLB 派了台连不上的边缘这件事已经坐实。

## mihomo 的 DNS 配置，决定了它的解析视角

问题出在 mihomo 自己的 DNS 配置上。它的 `dns:` 段是这样的：

```yaml
dns:
  enable: true
  listen: 0.0.0.0:1053
  ipv6: false
  enhanced-mode: fake-ip
  fake-ip-range: 198.18.0.1/16
  fake-ip-filter:
  - geosite:cn
  - geosite:private
...
  default-nameserver:
  - 223.5.5.5
  - 119.29.29.29
  nameserver:
  - https://doh.pub/dns-query
  - https://dns.alidns.com/dns-query
  proxy-server-nameserver:
  - https://doh.pub/dns-query
  nameserver-policy:
    +.example.edu:
```

```yaml
  nameserver-policy:
    +.example.edu:
    - https://dns.alidns.com/dns-query
    - https://doh.pub/dns-query
    +.lan:
    - 192.168.1.1
    +.local:
    - 192.168.1.1
    geosite:cn:
    - 223.5.5.5
    - 119.29.29.29
```

这里有两个容易看混的字段：`default-nameserver` 是用来解析上游域名本身的，不是给你查业务域名的；真正给业务域名用的默认上游是 `nameserver`，而它是两个 DoH。`nameserver-policy` 里没有这个站点的单独条目，按匹配它落在 `geosite:cn` 那一支，写的是 UDP 的 `223.5.5.5` 和 `119.29.29.29`。

有意思的是结果对不上：策略写着 UDP，但 mihomo 给出的答案跟直接问 `223.5.5.5` 得到的并不一样。为什么会这样我没能坐实，它内部怎么转发、DoH 请求从哪个出口发出，都还排除不掉，能确定的只是视角差异：DoH 上游看到的边缘和国内 UDP 看到的边缘不是同一台。另外这份配置里没有 `respect-rules` 这个键，mihomo 自己的 DoH 请求不受代理规则影响。

## 内网 DNS 服务器是路由器，回答问题的却是 mihomo

还有个前提得搞清楚：PC 明明把 DNS 服务器设成路由器，解析结果怎么就像出自 mihomo。路由器上的 nft 规则给了答案：

```
ip saddr { 192.168.1.223, 192.168.1.244 } return comment "proxy host self, bypass (loop fix)"
ip saddr @proxy_us_clients meta l4proto { tcp, udp } th dport 53 dnat ip to 192.168.1.223:1053 comment "US dns -> laptop"
ip saddr @proxy_sg_clients meta l4proto { tcp, udp } th dport 53 dnat ip to 192.168.1.223:1053 comment "SG dns -> laptop"
```

```
set proxy_us_clients {
	type ipv4_addr
	flags interval
	comment "美国组设备"
	elements = { 192.168.1.125, 192.168.1.244,
		     192.168.1.247 }
}
```

PC（`192.168.1.125`）就在 `proxy_us_clients` 集合里，它发出的 53 端口请求在路由器的 prerouting 阶段被 DNAT 到了 `192.168.1.223:1053`，也就是 mihomo 监听的 DNS 端口（`192.168.1.223` 和 `192.168.1.244` 是同一台代理机的两张网卡）。而 PC 自己看到的设置仍然是：

```
Current DNS Server: 192.168.1.1
       DNS Servers: 192.168.1.1
```

配置里写着路由器，真正回答问题的是 mihomo。国内网站的解析视角被代理软件决定了，前面那个不一致就是这么来的。

## 刷不动缓存：这一版 API 没有清 DNS 缓存的端点

改配置之前我先试着把缓存刷掉，免得重启。mihomo 带 RESTful API，照着接口发 POST：

```bash
sshpass -p '<口令>' ssh windy2@192.168.1.244 'curl -s -X POST -H "Authorization: Bearer <token>" http://127.0.0.1:9090/cache/flush/dns; echo; sleep 1; for i in 1 2 3; do dig +short @127.0.0.1 -p 1053 www.example-site.cn A | tail -1; sleep 2; done'
```

```
404 page not found

198.51.100.10
198.51.100.10
198.51.100.10
```

404，答案纹丝不动。三天后只读复核时又确认了一遍，这是端点本身不存在，不是鉴权的问题：

```
--- GET /version (带鉴权) ---
{"meta":true,"version":"v1.19.33"}
--- GET /cache/flush/dns (带鉴权, 只读探测) ---
404 page not found
 [http 404]
--- GET /cache/fakeip/flush (带鉴权, 只读探测) ---
 [http 405]
```

`/version` 正常返回，说明 API 活着、鉴权也过了，真没通过会是 401 而不是 404。`/cache/fakeip/flush` 返回 405 是很好的对照组：端点存在，只是只收 POST。所以这版 mihomo 有清 fakeip 的接口，没有清 DNS 缓存的接口，想让新答案生效只能改配置后重启容器。

## 修复：钉住上游、重启、再刷本机缓存

先备份再改配置，把这个域名的解析强制交给国内 UDP DNS：

```bash
sshpass -p '<口令>' ssh windy2@192.168.1.244 'cp /home/windy2/mihomo/config.yaml /home/windy2/mihomo/config.yaml.bak-20261102-example-site && sed -i "s|^    geosite:cn:|    +.example-site.cn:\n    - 223.5.5.5\n    - 119.29.29.29\n    geosite:cn:|" /home/windy2/mihomo/config.yaml && sed -n "48,58p" /home/windy2/mihomo/config.yaml'
```

改完是这样：

```yaml
  nameserver-policy:
    +.example.edu:
    - https://dns.alidns.com/dns-query
    - https://doh.pub/dns-query
    +.lan:
    - 192.168.1.1
    +.local:
    - 192.168.1.1
    +.example-site.cn:
    - 223.5.5.5
    - 119.29.29.29
```

然后重启 mihomo：

```bash
sshpass -p '<口令>' ssh windy2@192.168.1.244 'docker restart mihomo && sleep 4 && dig +short @127.0.0.1 -p 1053 www.example-site.cn A | tail -1'
```

```
mihomo
198.51.100.20
```

这一条重启同时做了两件实事：加载新的 `nameserver-policy`，清掉 mihomo 进程内的 DNS 缓存，答案随即变成好节点。远端算是修好了，可 PC 这时仍然打不开：

```
PC完整访问: HTTP 000 15.001487s
```

因为本机还有一层缓存。mihomo 是一层，客户端的 systemd-resolved 又是一层，DNS 答案在这两层各存了一份：

```bash
getent hosts www.example-site.cn; resolvectl flush-caches 2>/dev/null; sleep 1; echo '--- after flush ---'; getent hosts www.example-site.cn
```

```
198.51.100.10 www.example-site.cn.w.example-cdn-gslb.com
--- after flush ---
198.51.100.20    www.example-site.cn.w.example-cdn-gslb.com
```

刷完之后再访问：

```
PC完整访问: HTTP 302 0.189395s
```

302 是站点对未登录请求的正常跳转，和修复前用 `--resolve` 打到好节点时的结果一致。

## 复核：那台「死」节点后来自己活了

11-05 我做了一轮只读复核，只用查看类命令，想确认这套结论再过一天还站得住。结果有点出人意料：

```
=== ping 旧坏IP 198.51.100.10 ===
--- 198.51.100.10 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2005ms
rtt min/avg/max/mdev = 22.608/22.717/22.785/0.078 ms
=== ping 旧好IP 198.51.100.20 ===
--- 198.51.100.20 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 30.657/31.351/31.816/0.500 ms
=== ping 当前IP 198.51.100.30 ===
--- 198.51.100.30 ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 60.390/60.548/60.737/0.143 ms
```

三台边缘 ICMP 全通，原先那台 `198.51.100.10` 的 TCP 443 已经 OPEN，用 `--resolve` 上去能拿到 302（0.274308s）。PC 这边现在解析到 `198.51.100.30`，访问是 `HTTP 302 / 0.365608s`，`nameserver-policy` 里那条 `+.example-site.cn:` 仍然在位生效。

也就是说，原来那台不是永久下线，只是当时从家里这条线路建连超时。它自己活过来了，也顺带说明好节点同样会随 GSLB 漂移：11-02 是 `198.51.100.20`，11-05 换成了 `198.51.100.30`。我修的从来不是某个 IP，而是解析视角这件事；真正把结论钉死的是那组只改 IP 的对照实验，不是等它自愈。

现在碰到「某个网站打不开」，我会先做两件事：在同一台机器上问两路 DNS，比对 CNAME 和 A 记录是否一致；再用 `--resolve` 对照两次，把「DNS 视角」和「这台 IP 能不能连」分开验证。
