# GOSIM 巡天智能体黑客松备战复盘：一天把基线从 4223 拉到 4846

## 背景

10 月 5 日凌晨，GOSIM "智能体巡天" 黑客松（survey26）正式开赛。题目很浪漫：你的智能体接管一台（模拟的）光谱巡天望远镜，在一整个观测季里自主决定每次曝光的指向、时长、观测程序和光纤分配——但它看不到真实天气，只能靠每 15 分钟一条的简报瞎猜，而且整场巡天的真实墙钟预算只有 900 秒。

这篇文章是开赛前一天备战工作的复盘。成绩单先行：

| 本地卡 | 官方示例基线 | 调整后 | Δ |
|---|---|---|---|
| L1 | 4458.6 | 4508.5 | +50 |
| L2 | 4767.7 | 4895.2 | +128 |
| L3 | 4288.3 | 4813.7 | +525 |
| L4 | 3378.5 | 5166.2 | +1788 |
| 均分 | 4223.3 | **4845.9** | **+623** |

## 情报先行：把静态站拆成文档

比赛平台是个 GitHub Pages 上的 Vue SPA，没有传统意义上的"文档页"可以爬。但 SPA 意味着所有内容都在 JS chunk 里。我把站点的前端 bundle 全拉下来，用正则把 minified 字符串字面量里的中文文档、规则全文、四张练习卡说明完整提取了出来，配上官方讲座的转写 PDF（微信群里发的），整理成五份需求文档进了仓库。

这一步的回报立竿见影：很多后来在代码里踩的坑，文档里其实都写了（比如"hit_count 是纯几何判定"这条，成了后面 pointing_offset 检测器的基础）。

**教训一：转写文本不可全信。** 讲座转写里"9900 秒"实际是 900 秒，`--cards ../local_cards/l1` 实际是 `--card ../local-cards/L1`。凡是关键数字和命令，一律以代码和书面文档为准交叉验证。

## 基线分析：分数都丢在哪

跑通官方示例后没有急着改代码，先做了失分归因。四张本地卡的基线剖面非常一致：

1. **限时观测请求完成率 0%** —— 代码里对 `observation_request` 消息类型零引用，系统白送的分（每卡最多 +200）一分没拿；
2. **required 必观测目标漏网 15 个**（合计 −750）—— 而且发现一个漂亮的反直觉 bug：失败次数越多的目标被指数级降权（0.7^attempts），**越失败越不再尝试**，沉底后再也排不上；
3. **900 秒墙钟只用了 4%** —— 节奏控制逻辑只降不升，锚点搜索常年最低档。

## 修复：三处改动，+623 分

- **请求感知调度**：解析 `active_requests`，给请求目标加调度加成，曝光时长受请求 deadline 约束（只有完整落在窗口内的曝光才计数）→ 三张卡各 +100；
- **required 豁免失败阻尼** + 末夜保底进入候选 → L4 从漏 8 个降到漏 1 个；
- **state_resync 账本重建**：Hard mode 的 data_loss 事件会作废一段观测，原代码作废后历史成败记录还在，被作废的目标继续背着"失败阻尼"无法重建。清零后 L4 直接 +1788。

还有一个隐藏较深的 bug：地震公告会在整个恢复期（约 17 天）每个 slot 重播，而故障检测的证据池要求"干净"样本——地震公告让所有样本永久不干净，故障证据冻结，后续的仪器故障永远报不出来。把地震从公告集合剔除后，三张卡各恢复 +100 举报分。

## 云端实战：LLM 活了，反而帮倒忙

把打包好的 agent 提交到平台跑练习卡 α–δ，云端和本地有个本质差异：**平台上的 LLM 是通的**（平台注入自己的模型代理）。本地调试时 LLM 调用全部失败走规则兜底，云端 night_advice 真的在每晚给建议。

结果日志里出现了这种东西：

```
avoid=['E', 'N', 'NE', 'NW', 'S', 'SE', 'SW', 'W']  duration x0.70
```

八个方向建议全避——等于今晚别干活了。同时曝光时长打 7 折，让一批处在及格线边缘的 required 目标过不了 0.5 的完成门槛。云端四卡 required 漏网 20/15/9/20，比本地严重一个量级。

修复方式是给 LLM 建议加"消毒层"：覆盖 7 个以上方向的全避建议直接丢弃（全场关闭自有公告机制处理）、时长缩放下限提到 0.85、required 目标对 LLM 避让建议只打 8 折。**LLM 的输出永远要过一层确定性校验，这个原则在 Agent 工程里怎么强调都不为过。**

另外平台的公开测试卡暴露了另一个形态差异：只有 7 夜的短赛季（本地卡都是 38 夜），"最后一夜再抢救"的逻辑根本来不及启动。改成了按赛季长度自适应的紧急窗口。

## 工程事故：子代理僵尸与输出竞争

诚实记录一个当天的事故。我把迭代调优任务派给编码子代理，它触到 2 小时上限报超时——但**实际上没有死**，继续在后台跑测试。我这边不知情也在跑，两边的测试进程共享同一个 `run_output/` 目录，结果文件互相覆盖。我一度拿着 L4 卡的消息流分析 L1 卡的故障，差点得出错误结论。

教训三条：

1. 并发实验必须隔离输出目录，或者用锁；
2. "超时"不等于"终止"，管理后台任务要确认进程真的退了；
3. 大任务切片要小到能在时限内闭环，两个小时的任务没人能盯住。

## 赛前状态

代码在 [gosim-survey26-agent](https://github.com/windy664/gosim-survey26-agent)（私有，赛后会按规则开源）：请求调度、required 保障、Hard mode 两个机制（data_loss 重建 + pointing_offset 探针）都已实现，本地四卡零回归验证。

剩余风险：pointing_offset 本地没卡能验证，只能等云端 γ/δ 的表现；L1 的故障举报在地震恢复期会被稀释，±100 分的取舍先挂起；模型额度指望"前 100 队跑通练习赛"送的 Kimi Coding Plan 兑换码。
