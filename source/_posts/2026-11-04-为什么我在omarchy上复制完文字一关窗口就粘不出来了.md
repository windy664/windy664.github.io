从 Ubuntu 换到 Omarchy 后，我最先不适应的不是窗口动画，而是剪贴板。在浏览器里复制一段文字，关掉浏览器，按 Super+V 想粘到终端—— nothing。再按一次，还是 nothing。不是快捷键没生效，是剪贴板里的内容跟着源应用一起消失了。

这件事在 Wayland 上不是 bug，而是协议设计。Omarchy 本身已经做了一些补救，但补救不等于完全兜底。最后我额外装了一个 `wl-clip-persist`，又把官方那套 Super+C / Super+V 的复制逻辑读了一遍，才算把这事理顺。

##  Wayland 剪贴板为什么一关应用就丢

X11 时代剪贴板内容由 X server 保管。你按 Ctrl+C，应用把数据交给 X server，之后哪怕应用立刻退出，X server 手里还有一份，别的应用来要照样能给。这是很多人习惯了二十多年的模型。

Wayland 走了另一条路。它的核心协议里没有一个"中央服务器"长期保存剪贴板数据。复制操作发生时，提供数据的应用（data source）会创建一个 `wl_data_source` 对象，向 compositor 声明"我现在提供某某 MIME 类型的内容"。compositor 把这个 source 标记为当前 selection，但当别的应用请求粘贴时，compositor 并不直接给数据，而是让请求方和源应用建立点对点连接，由源应用实时把数据流传过去。

这意味着：**源应用必须活着，剪贴板内容才存在**。它一退出，`wl_data_source` 对象被销毁，selection 要么变空，要么指向一个已经不存在的数据源。表现出来的就是你复制完文字，源窗口一关，粘贴就失效。

这个设计有它的道理：剪贴板里的敏感内容不会被 compositor 长期持有，隐私模型更干净；compositor 也不用为一份大图片或视频占内存。但代价就是用户会看到"一关应用复制内容就消失"这种反直觉行为。

##  Omarchy 自带的剪贴板历史已经做了一手兜底

Omarchy 默认跑了两条 `wl-paste --watch` 守护进程，负责把复制的内容抓进 quickshell 的剪贴板历史面板：

```text
torin    2881239  0.0  0.0   3172  1916 ?  S  07:22  0:00 wl-paste --type text --watch /usr/share/omarchy/shell/plugins/clipboard/capture.sh text
torin    2881240  0.0  0.0   3172  1916 ?  S  07:22  0:00 wl-paste --type image/png --watch /usr/share/omarchy/shell/plugins/clipboard/capture.sh image/png
```

`capture.sh` 会把内容写进 Omarchy 的剪贴板历史数据库。按 Super+Ctrl+V 可以打开历史面板，从里面把之前复制过的内容再选出来。换句话说，如果你复制后立刻源应用崩溃或退出，数据已经进了历史面板，手动去翻还能找回来。

但它不是自动兜底。每次粘贴都按历史面板找上一条，效率太低；而且有些应用只把内容放到 PRIMARY selection（鼠标选中即复制），有些只放到 CLIPBOARD selection（Ctrl+C 显式复制），历史面板不一定两种都按你预期的方式保留。我想要的是：按 Super+V 直接粘出上一条内容，不管源应用还在不在。

##  wl-clip-persist 就是为此而生的

`wl-clip-persist` 的做法很直接：它作为一个常驻客户端，监听 CLIPBOARD selection 的变化。每次有新内容被复制，它立即从原应用那里把数据读出来，然后自己重新 offer 一份完全相同的 selection。原应用退出后，selection 的所有权已经转移到了 `wl-clip-persist` 手里，粘贴请求由它来回答。本质上它用另一个客户端替代了 X server 的"长期保管"角色。

在 Arch / Omarchy 上，这个包在 AUR 里：

```bash
$ yay -S wl-clip-persist
```

装好后我手动验证了一圈：

```bash
$ hyprctl reload 2>&1 | head -1
ok
$ setsid wl-clip-persist --clipboard regular >/dev/null 2>&1 &
$ sleep 1
$ pgrep -af wl-clip-persist
4035069 wl-clip-persist --clipboard regular
$ echo -n "持久化测试-甲乙丙" | wl-copy && wl-paste
持久化测试-甲乙丙
```

`regular` 模式表示只持久化 CLIPBOARD，不灭失；`clipboard` 参数也可以选 `all`，把 PRIMARY 也一起接管。我只需要 Ctrl+C 复制的那一份，所以 `regular` 就够了。

验证完功能，再把它写进开机自启动。Omarchy 的 Hyprland Lua 配置里，`~/.config/hypr/autostart.lua` 是用户级入口：

```lua
-- ~/.config/hypr/autostart.lua
o.launch_on_start("wl-gammarelay-rs")
o.launch_on_start("wl-clip-persist --clipboard regular")
```

重启登录后它会自动拉起。从那以后，源窗口关掉再按 Super+V，内容还在。

##  装好 wl-clip-persist 之后剪贴板变怪？先看它活着没

`wl-clip-persist` 在 Reddit 和几个 compositor 的 issue 区都有崩溃报告。niri 用户那边尤其多：它接管 selection 后如果 compositor 对 selection 所有权的管理有差异，偶尔会 segfault。我目前用的 Hyprland Lua fork 还没遇到崩溃，但把排查命令放在手边：

```bash
$ pgrep -af wl-clip-persist
```

如果发现粘贴行为突然异常，先确认这个进程还在不在。不在了重新拉起来就行，问题多半不复杂。

##  QQ 右键复制不了，这锅 wl-clip-persist 不背

装好 `wl-clip-persist` 后我顺手试了一下 QQ 右键复制。QQ 是基于 Electron 的 Linux 客户端，右键菜单里有复制选项，但点了之后剪贴板里并没有内容。这个和 Wayland 的剪贴板模型无关，是 QQ 自己的问题——它的右键菜单没有正确把选中文本写进 `wl_data_source`。

对这种情况，只能绕过 QQ 的菜单，用系统级快捷键复制。Omarchy 给了一套统一的 Super+C，它会判断当前焦点窗口是不是终端，再决定发 Ctrl+C 还是 Ctrl+Insert：

```lua
-- /usr/share/omarchy/default/hypr/bindings/clipboard.lua
local function send_shortcut_once(mods, key)
  return function()
    hl.dispatch(hl.dsp.send_key_state({ mods = mods, key = key, state = "down" }))
    hl.timer(function()
      hl.dispatch(hl.dsp.send_key_state({ mods = mods, key = key, state = "up" }))
    end, { timeout = 50, type = "oneshot" })
  end
end

local function active_window_is_terminal()
  local window = hl.get_active_window()
  if not window then return false end
  for _, tag in ipairs(window.tags or {}) do
    if tag:gsub("%*$", "") == "terminal" then
      return true
    end
  end
  return false
end

local function universal_clipboard_shortcut(default_mods, default_key, terminal_mods, terminal_key)
  return function()
    if active_window_is_terminal() then
      send_shortcut_once(terminal_mods, terminal_key)()
    else
      send_shortcut_once(default_mods, default_key)()
    end
  end
end

o.bind("SUPER + C", "Universal copy", universal_clipboard_shortcut("CTRL", "C", "CTRL", "Insert"))
o.bind("SUPER + V", "Universal paste", universal_clipboard_shortcut("CTRL", "V", "SHIFT", "Insert"))
o.bind("SUPER + X", "Universal cut", send_shortcut_once("CTRL", "X"))
o.bind("SUPER + CTRL + V", "Clipboard manager", "omarchy-shell shell toggle omarchy.clipboard")
```

这套设计的意图很清晰：不管你当前是普通应用还是终端，Super+C 统一管复制，Super+V 统一管粘贴。普通应用发的是 Ctrl+C / Ctrl+V；终端里自动切换成 Ctrl+Insert / Shift+Insert，因为终端默认是 Ctrl+Shift+C/V，DHH 估计是想让 Mac 习惯的人少记一个组合键。

原生快捷键也没被禁用。图形应用里 Ctrl+C/V/X 照样能用，foot 终端里 Ctrl+Shift+C/V 也照样能用。两套并存，所以一开始会 confused，但用熟了 Super+C/Super+V 之后，确实不用再关心当前焦点是不是终端。

QQ 的问题用 Super+C 复制就绕过去了。wl-clip-persist 负责让它在 QQ 关闭后仍然能粘出来，这是两条独立的链路。

##  隐私是一点真实代价

`wl-clip-persist` 会长期持有你最后复制的内容。如果你刚复制过密码、token、私钥片段，这些信息在它的进程里有一份镜像。Omarchy 自带的 `capture.sh` 会跳过标记为 sensitive 的剪贴板状态，但 `wl-clip-persist` 不区分敏感与否，它只是机械地重新 offer selection。

我的做法是在复制密码时先用密码管理器的自动填充，避免把密码放上剪贴板；万一复制了敏感内容，可以清一次剪贴板：

```bash
$ wl-copy --clear
```

这条命令会把 CLIPBOARD selection 置空，`wl-clip-persist` 也会跟着失去可持久化的内容。

##  复盘

这件事本质上不是"Omarchy 缺了什么功能"，而是 Wayland 的剪贴板协议把持久化责任推给了客户端。X11 帮你保管，Wayland 不保管，需要你自己雇一个保姆。

Omarchy 的保姆是历史面板，它把内容存起来供你手动检索；`wl-clip-persist` 是另一个保姆，它让普通粘贴继续像 X11 时代那样工作。两个保姆各有所长，我最后选择都雇上：历史面板用来找很久以前复制过的东西，`wl-clip-persist` 用来保证"刚复制的内容关掉窗口还能粘"。

如果以后剪贴板行为变怪，我的排查顺序已经固定：先看 `pgrep wl-clip-persist`，再看 `wl-paste` 两条 watch 进程，最后才怀疑 Hyprland 或具体应用。这条链路不复杂，但第一次遇到时确实容易把锅扣在快捷键或应用头上。
