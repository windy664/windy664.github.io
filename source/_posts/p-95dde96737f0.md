这个项目是我 2026 年 10 月拿去参加 GOSIM 智能体应用黑客松的作品，OctoDining，做食堂餐饮预算规划：把每月可支配生活费换算成每日饭钱，先给出一周餐表草案，人确认之后按表执行。

参赛要求里有一条叫 Agentic。我当时的理解是界面能跟 Agent 说话、Agent 能给出建议。做出来的东西能聊天也能给建议，离「Agent 参与完成任务」还差一截。让我停下来的不是评审意见，是我在 git 里翻出一处对不上：源码已经在调宿主的 Agent，manifest 却没申请这个能力。

<!-- more -->

下面写的是那之后的返工。模型的自由文本怎么压成结构化编号，省下来的钱怎么交给应用算而不是模型口算，写入前怎么设两道人工闸门，授权被拒、限流、超时、取消这几条路怎么一一落到界面上。

代码和报文都取自仓库，可以对着看：<https://github.com/windy664/OctoDining>

## 一个说自己 Agentic 的 App，第一版其实在演

OctoDining 就是这个项目，拿去参加 GOSIM 智能体应用黑客松，做食堂餐饮预算规划。

应用本体是 OctoScript 写的，跑在 OctoSense Shell 里。宿主提供一个叫 octos 的 Agent，小程序靠 manifest 里声明的 `octos.turn.start` 能力把活派给它。

从 9 月 28 日第一次提交到 11 月 3 日收尾，master 上 88 个提交把版本从 0.1.0 推到 1.12.0。让我愣住的不是版本号，是 git 里一处对不上的地方。

第一版的源码已经在调宿主 Agent（`b1f1b55`，那个模板当时才 192 行）：

```diff
+    host.request("octos.turn.start", {text: payload}, |result| {
+        isWaiting = false
+        if result.is_ok {
+            if result.data != nil && result.data.text != nil { agentAnswer = result.data.text }
+            else { agentAnswer = result.data.to_json() }
+            ui.mode.set_text("运行模式：Rinx + Octos Agent")
+        } else {
+            agentAnswer = local_preview_answer()
+            ui.mode.set_text("运行模式：本地预览（Octos 未连接）")
+        }
```

同一个提交里的 `bundle/manifest.json` 只声明了 `storage` 和 `net` 两个能力，`network.hosts` 还指着模型服务的域名。源码要的能力 manifest 没申请，manifest 申请的 `net` 源码又没走。

更要命的是失败分支：模型没通就直接 `local_preview_answer()` 兜底，界面上只改一行「运行模式：本地预览（Octos 未连接）」。用户眼前是一段像模像样的建议，但那句话可能压根不是模型写的。

第一版整个界面上跟模型状态有关的只有一个 Label，初始写着「运行模式：等待首次请求」，请求回来就变成上面那两种之一。没有取消按钮，也没有第二种说法。

## 模型接口通了，不等于 Agent 接通了

这题我误判过三次，每次都是把「某一步通了」当成了「Agent 接通了」。

第一次是上一段会话留下的。为了绕开 Rinx 宿主的问题，我直接调 DeepSeek 接口，也确实拿到过回复。当时我在会话里写下的原话是：「此前为了绕开 Rinx 问题直接调用 DeepSeek，只能说明模型接口可能可用，不能证明系统 Agent 已接通。」

第二次是内核层面。Octos 内核里 DeepSeek provider 能跑通模型，看上去链路是通的。可内核能工作，跟 Shell 里一个应用真被装载、真被授权，是两件事。

第三次最像真的：宿主自带的一组端到端测试全绿。但那组测试里被测的应用是 News，OctoDining 根本没装上去，首次授权也没人点。

「接通」和「没接通」长什么样，记录里其实分得清：

```json
  "app_version": "1.2.1",
  "host": "OctoSense Shell 4a541777 / Octos 2.0.3-rc.13 056173e",
  "provider": "minimax-cn",
  "model": "MiniMax-M3",
  "route": "https://<provider-host>/v1",
  "data_start": "fresh app data with no plans-a.json or plans-b.json; initial UI summary 已计划 ¥0.00 · 剩余 ¥32.00",
  "auth": "fresh Shell profile; first-use consent accepted; consent.json allowed=true",
```

宿主是哪个版本、provider 配了没有、路由通到哪、授权同意没有，四项摆在一起才算数。少一项，就像上面三次误判那样，只证明了一半。

后来我干脆把这件事写成一道构建期的硬检查。往 Rinx 分发目标同步时，目标 manifest 必须声明 `octos.turn.start` 且不能声明 `net`，不满足直接中止构建：

```python
if args.rinx_app:
    manifest_path = args.rinx_app / "bundle/manifest.json"
    manifest = json.loads(manifest_path.read_text(encoding="utf-8"))
    capabilities = set(manifest.get("capabilities", []))
    if "octos.turn.start" not in capabilities or "net" in capabilities:
        raise SystemExit("Rinx target must request octos.turn.start and must not request net")
```

从那以后，能力声明变成一条能跑的前置条件，不再是文档里的一句话。

还有一道更早的检查，在请求发出去之前就拦人：

```octoscript
fn ask_agent(){
    if agentBusy { return }
    if candidates.len() == 0 || candidateStamp == "" || candidateStamp != selection_stamp() {
        ui.agent_result.set_text(L("候选已失效，请重新查找。", "Options expired. Search again."))
        return
    }
    let condition = read_conditions()
    if condition == nil {
        agentChoice = -1
        agentStamp = ""
        ui.agent_result.set_text(L("当前条件已不可用，请重新查找候选。", "Current settings are invalid. Find options again."))
        return
    }
```

三种情况：上一次请求还没回来、候选已经失效、当前条件读不出来（预算上限、忌口这些约束），都是直接 `return`，请求都不发。拿一份过期的条件去问模型，回来的答案也用不了。

## 少写一行 manifest，App 里就没有 Agent

`197d252` 这一个提交同时改了两处，看着像两件事，其实是一件：让应用能真的向宿主要建议。

manifest 那边：

```diff
   "capabilities": [
     "storage",
-    "net"
+    "octos.turn.start"
   ],
-  "network": {
-    "hosts": [
-      "<provider-host>"
-    ]
-  },
   "schema": 1,
-  "version": "1.0.0"
+  "version": "1.2.0"
```

`net` 换成了 `octos.turn.start`，指向模型服务的那块 `network.hosts` 整块删掉。应用不再自己直连模型服务，请求一律走宿主，能力声明也跟着源码改了。

另一半在 prompt 里。以前我让模型「给一段理由」，自由文本没法核验，也没法撤销。改完是让模型在给定的候选里挑一个序号：

`仅返回 JSON：{"choice":候选序号(从1开始，无法推荐则0),"reason":"简短取舍理由"}。不要提供其他文本。`

序号是应用能验的东西，自由文本不是。同一个提交后面还跟着三个修补：`7b03a97` 丢弃迟到的回调，`b218b42` 给返回类型加校验，`ce48810` 在调 Agent 之前先确认当前条件还算不算数。

输出降成结构化编号之后，才谈得上校验。回来这一段要做三层检查，一层不过就当没收到：

```octoscript
        agentState = 1
        refresh_home_engine()
        let answer = nil
        try { answer = r.data.text.parse_json() } { answer = nil }
        if !answer.is_object() {
            agentChoice = -1
            agentStamp = ""
            ui.agent_result.set_text(L("Agent 已回复，但建议格式无法核验。请自行查看候选。", "The Agent replied in an invalid format. Review the options yourself."))
            return
        }
        let choice = -1
        try {
            let value = answer.choice
            if value.is_number() { choice = value }
        } { choice = -1 }
        if !(choice >= 0 && choice <= candidates.len() && choice == floor(choice)) {
            agentChoice = -1
            agentStamp = ""
            ui.agent_result.set_text(L("Agent 已回复，但建议格式无法核验。请自行查看候选。", "The Agent replied in an invalid format. Review the options yourself."))
            return
        }
```

能解析成对象是一层，序号是不是整数、有没有越界是二层，回复到达时候选条件有没有变是第三层（在前面就判掉了）。任何一层不过，`agentChoice` 都还是 -1，界面上不会出现「Agent 建议」那个角标。

落到盘上的东西也跟着变了。模型交回来的是一句建议和一个序号，写进计划的却是菜单里真实的那一条：

## 我改错了什么：把首页做成了聊天框

这个项目里最贵的三个决定都不是技术决定，是用户三次把我拽了回来。

第一次是首页。我那会儿理解的 Agentic 就是「用户先说话，应用再回应」，于是首页顶上放输入框，等人先提需求。用户直接给了另一套：

> 主页也不应该是一个聊天框架，而是一个为你推荐的餐品，基于历史or算法or餐表，然后下面才是一个输入框啥的可以跟agent讲话这样可以调整餐表，副界面是我的一周餐表内容

我当时的回话是「明白，我刚才把首页做成了『先输入再推荐』，方向还是偏了」。改法是把推荐提到最上面，输入框挪到下面，一周餐表单独一个页面。

回头翻第一版的界面，确实就是你说的那样，一个输入框加一个按钮：

第二次是 Agent 的作用没被讲出来。用户问「你是不是没有突出agent的作用 还是说 我们这个项目开发中没怎么开发agent」。我承认，那阵子上传的视频基本只展示了预算和餐表。

第三次我把评审流程当产品功能做了一轮。用户的话不客气：「入围建议全部跟我们产品一点关系都没有，你现在要做的是完善产品功能！」还有一句我记到现在：「我们是做产品的，不是走形式主义的」。

## 模型只准在我给好的选项里挑

七日草案是本地规则排出来的，我一开始想让模型去重排整周，后来改了主意。菜单快照里有 1,497 条商品，把整份清单丢给模型挑，等于让它重新发明一餐。它只需要在我给的编号里选。

所以选项是应用先算好的。`prepare_week_agent_offers()` 从草案里挑最多 5 个日期，每个日期去菜单里找替代品，筛的条件全挤在一条 if 上：不比原菜贵、菜名不同、符合这个餐次、默认到店时间在营业时段内、没被我拉黑过；每个日期最多留 2 个。

每个日期只给 2 个、整周只给 5 个日期是刻意的。选项一多，模型要在几十个编号里比较，理由也会跟着变长；一个都凑不出来时，选项文本会写「当前草案没有可核验的换餐选项，仍可手动逐餐调整」。

这段跑完，编号选项也一并生成了：每个日期一行原菜，下面挂替代品的编号、价格、店铺、营业时段，前面还带一行账目，写这个日期已计划多少、日预算是多少。模型看得到账，但那只是账，不是让它算账的许可。

给模型看的就是这个文本，`docs/AGENT-TASKS.md` 第 7 行写死了规矩：「Agent 不搜索整份菜单，不编造新菜名、价格、营业信息、营养或过敏原，也不替用户写入计划。」

提示词把这层约束又说了一遍：「只可从下列已验证的日期和餐品选项中提议调整，每个日期最多选择一个替代品」，返回格式是 `{"changes":[{"meal":…,"option":…}],"reason":…}`，并且要求 `meal` 逐字复制选项列表里那个日期文本。

回来之后逐条验：编号越界、日期重复、数组不对、理由不是字符串，任何一条不合法，整批提议作废。

## Agent 挂掉的时候，App 还得能让人吃饭

「模型不听话」我按格式问题处理掉了。还有更难的一半：模型根本不回话。

## 两道闸门，和一次读回

Agent 的输出最多改草案。草案要人点确认才写盘。写盘之后立刻把文件读回来重验一遍，才算成功。

这条链是：建议 → 草案 → 用户确认 → 写入 → 读回核验。链上没有一个地方写着「我觉得写成功了」。

第一道闸门是「应用建议到草案」。`apply_week_agent()` 先查五个过期条件，再在写进草案之前把草案期的规则重跑一遍：替代品不能比原价贵，必须符合该餐次，默认到店时间必须落在营业时段里。任一条不满足，整批放弃，界面写「换餐条件已变化，未修改草案。」

```octoscript

```

写完立刻 `fs.read` 读回来比对字节串，再走一遍 `read_record()` 里的 `record_valid()` 完整校验：餐次的价格、名称、店铺、营业时段都要和当前菜单对得上，菜单更新过、旧记录的菜价还对不上，整份记录都会被判无效。两者都过才算写入成功。

`plans-a.json` 和 `plans-b.json` 轮流写，写坏一份不丢历史。真失败时的文案是「保存失败：未能写入并核验。上一份有效计划已保留，请检查存储后重试。」

单餐那条路也一样，候选卡上先给一行证据，再让 Agent 在卡片上加一个角标。「选它后今日余 ¥X」是应用本地算的，Agent 没参与这一步：

![候选卡：证据行与选它后今日余](/posts/octodining-agent-loop/02-candidates.png)

落盘之后的读回是另一种证据强度，机器写出来的文件。1.12.0 那次的 `plans-readback.json` 是单行紧凑 JSON，`revision` 1、7 天 20 餐、`menu` 是 `gzis-snapshot`。下面截三段，省略号是我加的：

```text
{"schema":1,"revision":1,"last_date":"2026-10-13","days":[{"date":"2026-10-13",…
…{"date":"2026-10-16","daily_cents":3200,"meals":[{"slot":1,"product_id":1049,"cents":990,"name":"鱼蛋粉",…
…],"menu":"gzis-snapshot"}
```

`revision` 是写入代次，每次确认整周加一，迟到的回调靠它判废。

## 最后跑通的那一次，长这样

1.12.0 在 2026-10-13 同一天跑了两次独立的真实模型运行。同一个签名包，同一个 MiniMax-M3，金额却不一样，因为两次的草案起点不同。

先把两次分开说。

19:32 那次验的是 diff 卡，草案就绪时是待确认 20 餐、缺口 0，含 1 份副餐。我这台机器没有 Wayland 抓屏工具（grim、spectacle、import 都不可用），所以那次连画面都没有，证据是远程桥 `/snap?all=1` 的全量文本断言：

| 10-13 | 蛋肉炒饭 ¥12.00 → 鸡蛋炒米粉 ¥10.00 | ¥2.00 |
| 10-14 | 霸王炒鸡饭 ¥12.00 → 牛筋丸米粉 ¥10.00 | ¥2.00 |
| 10-15 | 鸡扒滑蛋饭 ¥11.50 → 火鸡拌面 ¥9.00 | ¥2.50 |

关键帧一共六张，串起来正好是这条链：首页、七天草案就绪、请求进行中（取消按钮在场）、提议摘要、逐条 diff 卡、确认读回。这里放三张：

读回 JSON 是另一种证据强度，机器写出来的文件，不是截屏。Agent 选的四餐逐条在盘上：10-14 午餐牛筋丸米粉 ¥10.00、10-15 午餐火鸡拌面 ¥9.00、10-16 午餐鱼蛋粉 ¥9.90、10-17 午餐筒骨汤香菇肉丝红薯粉 ¥8.00。

摘要行里还有第五笔 ¥0.20，对应 10-13 晚餐的鲜肉汤粉 ¥11.80。证据原文只逐条列了 4 笔午餐，这一笔是我拿摘要行和读回文件逐笔对照推出来的，属于推断。

所以这几个数字各有各的来路：¥11.10 来自远程桥的文本断言，¥9.30 来自帧缓冲关键帧，20 餐来自读回 JSON，1236×752、98 帧、63.6 秒来自 ffprobe。

这四步的证据强度不一样：文本断言、帧缓冲合成的视频、帧缓冲关键帧、读回 JSON。哪一步是画面，哪一步是断言，哪一步是文件，我按能核到的强度说。

## 还差什么

菜单快照停在 2026-09-28，没有现价、库存、营养和过敏原事实。「清淡」「少辣」能靠关键词做，「过敏」「素食」这类请求只能直接拒绝。这条改不动，除非有人去接实时菜单。

90 秒超时兜底至今没被真实慢请求触发过。1.11.6 的证据文档自己写着「超时兜底（90 秒无响应自动停止）本次未用真实慢请求触发，路径与取消共用同一复位逻辑（requestId 过期 + busy 复位 + interrupt），经代码审查与 card-host 回归覆盖」。

这句话我照抄，不写成「已验证」。要把它验掉，得故意造一个慢的 provider，那是另一件事。

1.7.0 那次只有 429。那次能证明的是 Shell 能加载应用、首次授权能完成、Agent 请求进了 Octos、人工选的候选保存后读回、重启后还在；没有模型建议，所以我不把 1.7.0 和 1.2.2 的证据拼成同一版记录。

模型建议只覆盖少数几个版本：1.2.1、1.2.2、1.8.13、1.9.0、1.11.0、1.11.6、1.12.0 留有真实模型证据，同一批证据里还有一份本机 mock provider 的联调记录，那是另一回事，不能和线上模型拼成一次。

授权拒绝那条路在 1.9.0 没复测，因为运行前 `consent.json` 就已经是允许状态。失败路径那组记录里也没有首次授权截图，`limits` 字段写得很直白：

```text
Failure paths were tested with consent state in an isolated profile. No first-use consent sheet capture, live model call, or Shell screenshot is included.
```

那个仓库比赛之后我没再动过，只做了清理和补文档。
