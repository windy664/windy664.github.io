# 一个人维护的 Rust 系统，是怎么迭代起来的

我宿舍里跑着一套自己写的个人助理 ru41：Rust 写的任务调度核心，挂着 QQ 机器人，管我的课表、作业、水电、RSS、实习信息。到现在 26 个 docker 容器，全是我一个人维护。

一个人维护系统最大的敌人不是 bug，是**迭代速度**。野心永远比时间多，任何一个改动如果都要半小时才能上线，那很多想法就会永远停在"改天再说"。这半年我把整套系统从单体改成了动态链接插件（.so）架构，这篇文章记一下这笔账：为什么改、改完快了多少、以及 Rust 插件化路上几个真实的坑。

## 单体时代的痛：改一行字，全连滚动 15 分钟

最早的 ru41 是一个主 crate 编译出一个二进制，所有附属功能（水电、RSS、比赛监控……）都是主 crate 里的模块，打成同一个镜像。生产机上是容器编排，每个功能一个容器，但镜像只有一个。

这意味着什么？我想给水电日报加一句话，流程是：

1. 改代码，本地全量编译主 crate（增量大改时好几分钟）
2. push，等 CI 构建完整镜像（约 10 分钟）
3. `docker save | ssh docker load` 传镜像
4. 滚动脚本把 20 多个容器**全部**停掉、重建、拉起

一次小改动，从写下第一行代码到线上生效，15 分钟起步。更难受的是爆炸半径：任何一个模块的 bug，编译不过就是整个系统发不出去；线上一个模块 panic，虽然容器隔离不会互相拖死，但共享镜像意味着你只能全量进退。

对于一个人维护的项目，这个成本会直接杀死"随手做个小功能"的冲动。

## 插件化之后：一个下午，三个功能

改成插件化之后，附属功能全部是独立的 crate，编译成 `.so`，核心二进制启动时按目录加载。核心只保留：任务调度、SQLite 存储、渠道网关（QQ/飞书收发）、插件握手协议。

上周六我顺手做了个图书馆附属，时间线大概是这样的：

- 下午 2 点：催还提醒写完，本地 `cargo test` 过，scp 一个 15MB 的 `.so` 到服务器，重启**一个**容器，上线
- 下午 3 点：发现 SSO 登录拿不到 JWT，查了跳转日志，40 秒一轮"改代码→本地编译→scp→重启看日志"的循环，十几轮之后定位到 JWT 藏在 302 Location 的 URL fragment 里（reqwest 自动跟随重定向会把 fragment 剥掉，得手动逐跳）
- 下午 4 点：顺手又加了 `/找书`（公开馆藏检索）和 `/追书`（样本库的书转出可借时推送），各自独立测试、独立部署
- 傍晚：用户（我自己）说"结果里想要封面"，扒了下前端代码找到独秀封面接口，又发了一版

一个下午，一个全新附属从零到上线，外加两轮功能迭代和一次线上排障。**每一步的部署成本都是 scp 一个文件 + restart 一个容器，30 秒级。**

对比单体时代的 15 分钟全连滚动，这就是插件化对个人开发者最实在的价值：不是架构好看，是**让"想到就做"重新变得划算**。

## 迭代速度的另一块：编译时间

部署快了，编译也得跟上。插件都是独立 crate，各自有自己的 target 目录，但每个插件都依赖核心的 `ru41` crate（走 path 依赖）——改一个插件，本地要先把核心 crate 编一遍，增量也要三四十秒。

后来做了两件小事：

1. **所有插件共享一个 target 目录**（`plugins/.cargo/config.toml` 里把 `target-dir` 指到 `plugins/target-plugins/`）。核心 crate 只编译一次，全部插件复用。第二个插件的增量构建直接降到 0.1 秒。
2. **换 lld 链接器**。Rust 默认的 GNU ld 在链接大 crate 时很慢，clang+lld 能砍掉一大截链接时间。

效果：单个插件的典型迭代编译从 ~37 秒降到 ~5 秒。这个数字配合 30 秒的部署循环，才是完整的"快"。

## 诚实的代价：Rust 插件化的三个坑

插件化不是免费的。Rust 没有稳定 ABI，这条路有几个必须正视的坑，我们每个都踩实了：

**1. ABI 边界靠协议，不靠类型系统。** 跨 `.so` 传递的类型必须收敛到一个独立的 `plugin-api` crate，插件和宿主都链接它，靠 API 版本号握手（版本不一致直接拒载，git commit 不一致打警告放行）。想用 Rust 类型系统在边界上偷懒，门都没有——两边的 `String` 都不是同一个 `String`。

**2. 每个 .so 静态链接一份 tokio，reactor 互不通用。** 这个坑最阴：插件里写 `Box::pin(async move { ... })` 直接返回给宿主驱动，第一个 reqwest await 就 panic "no reactor running"，panic 穿过 FFI 边界直接 abort 整个进程——我的 QQ 网关就这么被 `/找书` 一发打崩过。解法是 bridge 模式：插件的异步工作必须 spawn 到**插件自己**的 runtime 里，宿主只等一个无 reactor 依赖的 oneshot。所有异步入口都得过这座桥，漏一个就是线上事故。

**3. 不能热加载。** `.so` 加载后没法卸载，更新的最小单位是重启容器。好在容器本来就按功能隔离，重启一个容器影响面足够小。想要"热更新"的得想清楚自己要的是不是其实就是这个。

还有一个自己造出来的坑：共享 target 之后，**`cargo clean` 会把所有插件的产物一起清掉**。我第一次测的时候就纳闷为什么第二个插件也要全量编译——自己 clean 掉的。

## 什么时候该做、什么时候别做

如果你也是一个人（或者两三个人）维护一个 Rust 系统，我的判断标准变了几次之后稳定在一条线上：**当你发现"部署和编译成本"开始让你放弃做小功能的时候，就该拆插件了。**

反过来说，如果系统还只有三五个功能、改动频率以周计，插件化带来的协议设计和边界约束是净负担——单体挺好的，真的。

插件化对个人开发者的意义从来不是"架构先进"，而是把迭代循环的每一环（编译、部署、爆炸半径）都压到**不会打断心流**的量级。心流不断，野心才跟得上。
