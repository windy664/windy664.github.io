写这篇文章之前我数了一次生产机上的容器：三十二个，其中二十七个跑着同一个镜像里的同一个二进制。一台八G内存的旧笔记本，摆出中型机房的阵仗。不了解内情的人看到这一屏，多半会以为主人迷上了分布式系统，或者单纯是疯了。

## 二十七个容器到底吃多少内存

「拆这么多容器肯定很吃资源」，这是所有人的第一反应，包括一周前的我。这个直觉来自 Java 年代：一个 JVM 空载就要几百兆，三十个进程那还了得。它对 Rust 不成立。

实测数字，写这篇时在生产机上用 docker stats 采的。机器是 i5-8250U，四核八线程，内存 7.1GiB，系统当前用了 3.2GiB。二十七个 ru41 容器合计约 720MiB，明细如下：

| 容器 | 内存 | 干什么 |
| --- | --- | --- |
| worker | 134 MiB | 跑 agent 任务，全家最重的 ru41 容器 |
| 二十几个轮询容器 | 每个 10–21 MiB | 消息网关、课表提醒、录音、发布，各管一摊 |
| paraformer-asr | 662 MiB | 语音识别，int8 模型，拆出去的独立软件 |
| browserless | 323 MiB | 共享无头浏览器，拆出去的独立软件 |

二十几个进程各自隔离、各自监督的全部代价，加起来不到半GB，塞不满一个模型容器的零头。磁盘上更占便宜：所有 ru41 容器共用一个 2.5GB 的镜像，docker 的分层存储让第二十六个容器的磁盘成本跟第一个一样，几乎为零。

真正吃内存的从来不是「拆」这个动作，是模型和浏览器。官方 SenseVoice 镜像空载就要一点五个G，比二十七个 ru41 容器的总和还多，它在这台机器上连常驻资格都没有，后来换成 int8 量化方案，四百五十 MB。拆分的内存税低到可以忽略，这是整套架构能在一台旧笔记本上成立的物理前提。换成 Go 也成立，换成 Java 这套架构直接出局。

## 一个镜像怎么跑出二十七种活法

机制两句话讲完。compose 文件里用锚点钉住公共部分，每个服务只写自己不一样的那一行：

```yaml
x-ru41: &ru41-common
  image: ru41:local
  init: true
  restart: unless-stopped
  environment:
    RU41_CONFIG: /etc/ru41/ru41.toml
    RU41_DB: /data/state.db

services:
  qq:
    <<: *ru41-common
    profiles: [qq]
    volumes: *ru41-volumes
    command: ["--config", "/etc/ru41/ru41.toml", "--db", "/data/state.db", "qq", "run"]

  rss:
    <<: *ru41-common
    profiles: [rss]
    volumes: *ru41-volumes
    command: ["--config", "/etc/ru41/ru41.toml", "--db", "/data/state.db", "rss", "run"]
```

同一个二进制，靠命令行子命令决定自己这个进程的角色：qq 容器跑消息网关，blog 容器每五分钟轮一次发布目录，lecture 容器每分钟看一眼有没有新录音。镜像本身一份多用，Dockerfile 分三个阶段，Rust 阶段编主程序，第二个阶段把十几个插件的 .so 一起编出来，运行时是 node 的 slim 镜像，因为 agent 底座 Codex CLI 是个 npm 包。profiles 保证没配置的功能不会被 `docker compose up` 全部拉起，容器里加载哪些插件还能用环境变量白名单再滤一层。

容器在这里是进程的边界，不是软件的边界。

## 单进程是怎么死的

ru41 最早就是单进程，一个 Rust 程序装下所有功能。那个形态舒服得实打实：内存只有一份，日志只有一份，`cargo run` 一条命令就是全部部署。要不是出事，大概会一直跑下去。

出事是因为架构里有个前提站不住。附属功能全部以 .so 动态库挂载，插件跟宿主共享进程空间，插件里的 Rust panic 触发的是整个进程的 abort。某天一个插件里的异步任务跑错了运行时，宿主进程被直接带走，QQ 掉线，定时任务全停，正在转写的录音中断，所有功能同一秒死掉。

这种死法不是孤例，可以看活的。写这篇时生产机上的实况：`ru41-class-remind` 正躺在第十九次重启里，它崩在同类问题上的 panic 原文是：

```
thread '<unnamed>' (1) panicked at library/core/src/ops/function.rs:250:5:
there is no reactor running, must be called from the context of a Tokio 1.x runtime
fatal runtime error: Rust cannot catch foreign exceptions, aborting
```

它每几分钟死一次，docker 每几分钟拉一次。Erlang 的书里管这个思路叫 let it crash：出错的部分别硬扛，让它干脆死掉，交给外层的监督者拉起来。ru41 没有引 Erlang，但效果是同一个：class-remind 反复横死的时候，另外三十一个容器全部正常，QQ 照收发，笔记照整理，博客照发布。课前提醒这一门功能单独死着，其他一切无感。

## 拆完之后才有的秩序

拆分还顺带修好了几件单进程年代的旧毛病。图书馆插件改一行，重建它自己那个容器就行，QQ 网关不用断线重连，任何改动的生效都不再需要整个进程重启。哪个模块死循环了，`docker stats` 里它单独一行，一眼定位，烧的也只是自己那份 CPU。爬虫的 cookie 目录只有爬虫容器挂载，主程序的容器看不见，泄露也出不了那一舱。有点像船体的水密舱，一个舱进了水，关门，船接着走。

有人管这叫去中心化。不是的，三十二个容器挤在同一台机器上，共用同一个 docker daemon，中心化得很。拆开改变的不是权力结构，是故障半径：半夜崩了，哑掉一门功能，而不是整个机器人失联。

## 手写的名单

这套架构里最狼狈的教训跟设计无关，跟手抄有关。

插件这边，每个插件的注册表声明自己有什么活、多久跑一次：

```rust
pub static DEF: ModuleDef = ModuleDef {
    name: "lecture",
    schedule: |config| {
        let lecture = config.sources.get_or_default::<LectureSection>("lecture");
        vec![JobSchedule::simple(
            "lecture",
            LectureSection::DEFAULT_INTERVAL_SECS,
            lecture.is_ready(),
            lecture.not_ready_reason(),
        )]
    },
    // ...
};
```

部署那边，容器和活的对应关系长期是一份手写在滚动脚本里的名单，每个容器名对应一条启动命令，新建附属要有人记得加一行。两层各管各的，中间没有任何自动机制。

lecture 就是没人记得的那个。它是后来加的附属，名单里没有它，每次滚动更新都轮不到它。别的容器全换上新镜像了，它钉在几代之前的旧版本上，最后躺进崩溃循环，是排查录音失败那天顺带发现的。

修法是把名单删掉，滚动脚本改成自动发现：

```bash
while read -r name; do
  [[ "$name" == ru41-* ]] || continue
  ep="$(docker inspect "$name" --format '{{json .Config.Entrypoint}}' 2>/dev/null || true)"
  [[ "$ep" == *"/usr/local/bin/ru41"* ]] && NAMES+=("$name")
done < <(docker ps -a --format '{{.Names}}')
```

识别规则只有两条，名字以 ru41- 开头，entrypoint 是 ru41 本体，镜像被钉成无标签 ID 的掉队容器也能凭 entrypoint 认回来。重建前每个容器的完整 inspect 存进带时间戳的备份目录，env、挂载、网络逐字段恢复，回滚就是拿备份重建。改完之后新附属只要起了容器，下一次滚动自动覆盖，名单这个必须靠人脑维护的东西从部署里消失了。

为什么不直接上 Kubernetes，一步到位？因为一台单机跑 control plane 的开销比全部业务加起来还大，自动发现的好处，四十行 bash 就能先拿到。工具该有的体量是问题的体量。

## 协议死了才拆

机器上另外几个容器跟 ru41 不是同一个软件，拆出去的依据实践里收敛成一条：协议死了才拆。老 Unix 的说法是每个程序做好一件事，程序之间靠文本流协作，放到容器上，后半句就是契约：拆出去的容器跟主程序之间只有一条窄窄的数据通道，一个文件，一个接口地址。

智慧树是一个例子。它的接口层加密加浏览器环境，直连走不通，就拆一个 Playwright 加虚拟显示的采集容器，登录、枚举作业、写 report.json，主程序只读这个文件，不碰智慧树的网络协议，也不持有账号密码。这个形态在 Kubernetes 里叫 sidecar：辅助容器跟主容器共享卷，各干各的，拿文件交换数据。boss 直聘的爬虫同款，Python 镜像，不常驻，宿主机定时任务每天点两次名，爬完退出，产物是 boss_jobs.json。需要浏览器的活共享同一个 browserless 容器，HTTP API 直连，谁也不单独背一套 chromium。

反例更重要。学习通调研完发现协议层活着，签到、作业、图书馆全部 Rust 直连，一个容器都没加。sidecar 不是时髦，协议死了才是它的入场券，能直连的硬拆出去是画蛇添足。

## 不光彩的部分

拆的代价不粉饰。

日志立刻散了。二十七份日志没有总视图，排障要 `docker logs` 一个个翻。企业级的路子完整调研过一遍，采集、传输、索引、查询、留存五层摆下来，结论是伺候不起，Elasticsearch 光自己就要两个G内存，在这台机器上比业务功能优先级还高。现在的方案是轻量的日志聚合容器应急，Loki 加告警打算做成附属插件，告警直接走 QQ。还没做完，欠着。

配置一致性比单进程年代脆。全机一份配置文件，容器各有各的启动时机，改了配置要重启对应容器才生效。出过一次事：配置里一个段丢了，进程不知道，人也不知道，直到一条四十二兆的录音掉进错误的管道才暴露。单进程年代配置和进程天然同步，拆开后这条缝隙必须盯着。

镜像分发多了一步人肉。服务器没有公网，CI 构建出的镜像不走 registry 拉取，本机 `docker save` 打包，ssh 管道 `docker load` 灌进去，再滚动重建。好在所有容器共享一个镜像，搬的只是一份 2.5GB 的包。

还有一笔冤枉钱花在选型上。官方镜像的诱惑是「人家都打包好了」，实际上打包的人不知道你的机器只有八G内存。那次退回之后定下的规矩是：硬件约束放在选型的第一行，不是最后一行。

## 回到开头的问题

二十七个容器是失控还是设计。算完这本账，我的答案是后者，而且拆得起的底气全是数字给的：二十几个进程的隔离税不到半GB，第二十六个容器的磁盘成本跟第一个一样，一次崩溃只哑掉一门功能。同样的架构搬去 Java，物理上就不成立。

现在 `docker ps | grep -c Up` 的答案是三十二，这个数字还会涨。涨到内存见顶的那天，再谈合并。
