这次拆的是学习通——老师发签到、挂作业都用的那个平台。

动机还是那个老问题——时间窗口。老师发起的签到经常在上课前后突然出现，窗口只有一两分钟。人在路上、在楼梯间、在排队打饭的时候，手机弹出提醒，等走到教室坐下掏出手机，签到已经结束了。ru41 管着我的课表和提醒，但「提醒到了人来不及」这个问题，提醒本身解决不了，得让机器人替我盯着、替我在窗口里完成那一下点击。

先交代边界，这篇里的所有操作都只针对我自己的账号：签到自动化的范围是普通、手势、签到码、位置、拍照五类加照片驱动的二维码，作业只跟踪不代答，老师的二维码我不伪造。文章不含账号、密码、坐标和任何能定位到人的信息。

作业是顺带收进来的：截止时间散在详情页里，这件事跟签到一样适合交给机器人盯。后来发现作业这半边的协议和签到完全不是一个写法，反而比签到本身更值得记。

## 选型：协议是活的

超星系的签到工具，社区里最常见两类：协议库（直接发 HTTP）和签到脚本（大多要挂浏览器）。选型之前先看了一眼同生态的智慧树，那边我之前接过，协议层是死的：请求加密加浏览器环境校验，最后只能用一个 sidecar 挂着无头浏览器替它跑页面。一个附属功能背一个 Python venv 加一个浏览器进程，代价不小。

学习通这边探下来，协议是活的：登录、课程、活动、签到四个场景全是明文 HTTP + JSON/表单，没有浏览器依赖。那就没有 sidecar 的理由，Rust 模块内直连，形态和之前接校园卡 ecard 时一样。

动手前照例查了社区，这里记一条教训：搜索结果里标着「活跃」的项目不可信。我筛了一遍 GitHub 上的超星签到项目，好几个搜索快照里排在前面、简介写着持续维护的仓库，`pushed_at` 停在 2023 年。最后当参考实现的是 Samueli924/chaoxing（3.6k star，GPL-3.0，Python 协议库）。它的定位不是拿来用，是拿来当探针：登录可行性、响应结构、参数从哪来，先用它实测确认，再回 Rust 里自己实现。这个探针后来还派了个用场：它产出的登录密文，拿来做 Rust AES 实现的跨语言一致性测试向量。

还有一条网络层的实况：超星的 CDN 会拦数据中心 IP，但校园网和家宽出口实测没有被拦。机器人跑在宿舍服务器上，恰好是后者。

## 登录：固定 key 的 AES

登录端点 `POST /fanyalogin`，账号密码两个字段都要过一层 AES-128-CBC 加密再 base64。有意思的是 key 是写死的公开值，社区里人尽皆知，超星用它不是为了保密，是为了别让明文密码直接出现在请求体里：

```rust
const AES_KEY: &[u8; 16] = b"u2oh6Vu^HWe4_AES";

pub async fn login(&self) -> Result<()> {
    let response: LoginResponse = self
        .http
        .post(format!("{}{LOGIN_PATH}", self.passport_base))
        .form(&[
            ("fid", "-1"),
            ("uname", &cx_encrypt(&self.phone)),
            ("password", &cx_encrypt(&self.password)),
            ("refer", "https%3A%2F%2Fi.chaoxing.com"),
            ("t", "true"),
            ("forbidotherlogin", "0"),
            ("validate", ""),
            ("doubleFactorLogin", "0"),
            ("independentId", "0"),
        ])
        .send()
        .await?
        .json()
        .await?;
    if response.status != Some(true) {
        bail!("学习通登录被拒绝: {}",
            response.msg2.unwrap_or_else(|| "未知原因".into()));
    }
    self.save_cookies()
}
```

登录成功，`Set-Cookie` 下发的是域级 cookie（`_uid`、`_d`、`vc3`、`fid`），`.chaoxing.com` 全域共享，passport2 拿到的会话，mooc2-ans 和 mobilelearn 直接用。cookie 持久化到本地文件，进程重启先试 cookie，失效才走账密登录。频繁账密登录是最容易触发风控的行为，能复用就复用。

cookie 活没活、挂的是谁的会话，有一个请求能把两件事一起验掉：`GET /mooc/accountManage` 的页面里有个 `id="messageName"` 的输入框，value 就是当前登录人的真实姓名。

```rust
/// 当前登录用户姓名；会话无效时返回 None。
pub async fn realname(&self) -> Option<String> {
    let text = self.http
        .get(format!("{}{ACCOUNT_PATH}", self.passport_base))
        .send().await.ok()?.text().await.ok()?;
    let re = regex::Regex::new(r#"id="messageName"\s+value="([^"]*)""#).ok()?;
    Some(re.captures(&text)?.get(1)?.as_str().to_owned())
}
```

把整个协议面摊开看，其实就九个端点：登录、会话校验、课程列表、活动列表、preSign、签到、云盘鉴权、云盘上传、作业两件套。客户端常量里存的就是这张清单，一屏读完。

## 签到类型学：一个端点，六种形态

活动列表从 `POST /v2/apis/active/student/activelist` 来，每个课程一个请求。响应里关键字段是这些：

```json
{"result":1, "data":{"activeList":[
  {"id":1000175604104, "activeType":2, "type":3,
   "nameOne":"手势签到", "startTime":1793500000000, "endTime":1793500120000,
   "status":1, "userStatus":1, "attendNum":42}
]}}
```

`activeType` 是大类（2 是签到），真正决定怎么签的是 `type`：0 普通、1 拍照、2 二维码、3 手势、4 位置、5 签到码。`status` 1 进行中 2 已结束，`userStatus` 1 未签。轮询要盯的就是「进行中且未签」的组合。

这六种形态最终打到同一个端点 `GET /pptSign/stuSignajax`，先过一道 `preSign`，差异全在参数里：

| type | 形态 | 参数差异 |
|---|---|---|
| 0 | 普通 | `objectId=aaa`、`lat/lon=-1` |
| 3 | 手势 | 同普通 |
| 5 | 签到码 | 同普通 |
| 4 | 位置 | `name`=姓名、`address`=地址文本、真实 `latitude/longitude`、`ifTiJiao=1` |
| 2 | 二维码 | 服务端下发的 `enc` + `location` JSON，preSign 不一定走 |
| 1 | 拍照 | 照片先传超星云盘换 `objectId`，不走 preSign |

普通、手势、签到码三种其实是同一个请求，`objectId` 都填占位值 `aaa`，坐标填 -1，平台根本不看。位置签到要真实的经纬度和地址文本，这个在配置里存了一份默认值（我常待的位置），命令行可以临时覆盖。拍照走另一条路：先调云盘的 `uservalid` 拿 token，照片 `POST /upload`，响应里换回 `objectId` 再签。

二维码是个例外，它的 `enc` 参数下一节单讲。

## 自动签到的防风控设计

「能自动签」和「敢自动签」之间隔着一层设计。自动化的规则我定了三条：

**平台明确拒绝，绝不自动重试。** 对同一个活动反复撞签到接口，是所有机器特征里最典型的一个。所以自动签到的失败语义分成两档：平台给出明确拒绝（返回了失败文案），当场把这条活动标记为「已尝试」，附上平台原话发回执，然后停手；网络超时这类瞬时错误，快照不动，下一轮轮询自然重试。签到窗口常有一两分钟，最多也就重试一两次。

```rust
/// 平台明确拒绝后打「已尝试」标记：自动签不会对同一活动反复重试。
fn mark_auto_attempted(&self, course: &ChaoxingCourse,
                       activity: &ChaoxingActivity, note: &str) {
    let key = format!("{}#{}", course.course_id, activity.id);
    let _ = self.store.document("chaoxing_sign", &key).map(|doc| {
        doc.map(|doc| {
            let mut value = doc.value.clone();
            value["auto_attempted"] = serde_json::json!(crate::util::now());
            value["auto_note"] = serde_json::json!(note);
            self.store
                .put_document("chaoxing_sign", &key, Some(doc.revision), &value)
        })
    });
}
```

**轮询要省。** 初版固定 60 秒轮一次所有课程，后来改成跟课表联动：只在某门课上课前后 15 分钟的窗口里对那门课实轮询，其余时间睡大觉。签到只会出现在课表时间里，这个先验省掉了绝大部分请求。

**瞎了要喊。** 有一种情况比漏签更危险：接口返回成功但活动列表是空的。可能是会话半死不活，可能是接口改版，反正机器人以为天下无事。所以「全灭」本身成了一个告警信号——所有课程的活动列表一轮全空，就往消息出口喊一声，附上每个课程的错误信息。宁可误报，不可失明。

## 转折：伪造 enc 被平台当面打回

这是整个项目里我学得最重的一课，值得用一整节讲。

二维码签到的 `enc` 是个时效 token，由服务端生成、只随二维码图片分发，每十秒轮换一次。社区流传的说法是「enc 不校验，随便填个能签上」。我当时信了，代码里也照做了，初版自动签到里就有一个伪造 enc 的函数。

2026 年 10 月 23 日下午，一次真实的二维码签到窗口，平台对伪造值回了一句原话：

```
签到失败，请重新扫描。
```

不是参数异常，不是静默失败，是一句针对 enc 的、带引导语义的拒绝。伪造代码当天删掉了，commit 信息里专门写了一句「移除伪造 enc」，代码注释里留着这次实测的日期和原文，防止未来的我或者看到这段代码的人再信一次。

事后想，这个结论本来就该存疑：enc 这种「服务端生成、时效轮换、随图分发」的设计，存在目的就是防伪造客户端。社区结论说它不校验，等于说这个机制是摆设——一个被超星维护了这么多年的机制是摆设，概率上就不太对。我信它，不是因为验证过，是因为别人都这么说。

同一周里确证了它的另一面：enc 十秒轮换，但**窗口内历史值一直有效**。学生扫同学几分钟前截的图能签上——这不是逆向发现，是教室里的公共常识，我拿旧 enc 实测了一次，确实签上了。也就是说服务端校验的是 enc 的真伪，不是新鲜度。这个事实直接决定了后面照片方案的可行性。

## 照片驱动：拿不到 enc，就让人递过来

enc 拿不到伪造的路，也拿不到推导的路（后面科研线那节讲），但它有一个绕不开的物理约束：它只存在于二维码图片里。那就把「拿到图片」变成一条消息。

方案：老师现场展示二维码，我用手机拍一张（或者截一张同学的图），直接发给机器人；机器人下载图片，解码二维码，取出活动 id 和 enc，用这个真实的 enc 完成签到，回 ✅ 或 ❌：

```rust
pub fn decode_sign_qr(bytes: &[u8]) -> Option<DecodedSignQr> {
    let img = image::load_from_memory(bytes).ok()?.into_luma8();
    let mut prepared = rqrr::PreparedImage::prepare(img);
    for grid in prepared.detect_grids() {
        let Ok((_, text)) = grid.decode() else {
            continue;
        };
        if let Some(qr) = parse_sign_qr_url(&text) {
            return Some(qr);
        }
    }
    None
}
```

解码之后还要过一道身份判断：二维码内容必须 host 在 chaoxing.com 系，query 里同时带活动 id（`activeId` 或 `id`）和 `enc` 才算签到码。这样日常发来的其他图片（表情包、截图、文件）不会误触发签到流程，照常走 agent 通道。

实现上有个小细节：照片签到的 cookie 和签到轮询的 cookie 存了两份文件。两个进程各自持有一份会话，避免争写同一个会话文件把对方挤下线。

这套东西上线之后，二维码签到的实际操作是：手机震动 → 看到提醒 → 拍一张 → 发出去 → 收到 ✅。全程十几秒，比原来赶窗口从容得多。

## 90002：手势签到的风控攻防

自动签到跑顺了一阵，手势签到先出的事。

某天起，手势签到的直签请求开始被平台拒绝，错误码 90002，风控加了验证，直签通道被封。这意味着普通、手势、签到码三种里，手势从此签不动了。当时的处理是保底方案：手势签到改成「即发现即强提醒」，自动签不做了，人立刻来签。

但保底是保底，不是终点。超星的验证码体系和它别处的产品是同一套：`captcha.chaoxing.com` 的滑块验证，下发两张图——带缺口的底图（shade）和滑块拼图（cutout），验证通过换一个 validate 回来，带着它重放签到请求就过了风控。社区里有这套流程的构造方式，我把管线移植进了 Rust，最核心的是从两张图里算出缺口位置：

```rust
pub fn slider_gap_x(shade_bytes: &[u8], cutout_bytes: &[u8]) -> Option<u32> {
    let shade = image::load_from_memory(shade_bytes).ok()?.to_luma8();
    let cutout = image::load_from_memory(cutout_bytes).ok()?.to_rgba8();
    // cutout 可能带透明通道，先找出不透明区域的边界像素
    let has_alpha = cutout.pixels().any(|p| p.0[3] < 250);
    let opaque = |x: u32, y: u32| !has_alpha || cutout.get_pixel(x, y).0[3] >= 250;
    let mut boundary = Vec::new();
    let mut min_x = cw;
    for y in 0..ch {
        for x in 0..cw {
            if !opaque(x, y) { continue; }
            let is_edge = x == 0 || y == 0 || x == cw - 1 || y == ch - 1
                || !opaque(x - 1, y) || !opaque(x + 1, y)
                || !opaque(x, y - 1) || !opaque(x, y + 1);
            if is_edge {
                boundary.push((x, y));
                min_x = min_x.min(x);
            }
        }
    }
    // ...再对底图做全图 Sobel 边缘强度，与边界特征匹配出缺口 x
```

思路是两步：先从 cutout 提取滑块自己的形状特征（不透明区域的边界），再在底图上做全图 Sobel 边缘强度，算一次存表，滑动匹配时直接查。请求侧的参数构造（captcha_key、iv、token 三个 md5 的组合方式）社区已有定论，照抄即可。

手势签到恢复了全自动。事后看，90002 这次封堵反而把整个签到的健壮性往上抬了一层：风控从「偶尔抽查」变成了「常态化验证」，而验证码管线从此是常备能力，下次风控再变脸，改的就是一处。

## enc 科研线：把「能不能推导」当成一个实验

照片方案好用，但它依赖现场有人拍图。enc 能不能从公开信息推导出来？如果可以，二维码签到就完全自动了。这是个开放问题，值得当成一个实验来做，而不是拍脑袋下结论。

先立下约束：**采集永远不影响签到主链路**。两条采集线都是旁路的。

B 线，窗口探测：轮询发现某个课程有待签的二维码活动，就在后台抓学生端的详情页 HTML 和 preSign 响应体，正则抽 enc 候选入库。只入库，不拿去签。原始工件按活动 id 归档，失败了静默写 stderr，绝不阻塞提醒。

C 线，被动采样：每次照片解码出的真实 enc 都落一份 JSONL，签成功签失败都记。平台对无效 token 的拒绝原文，是分析 token 有效期的关键数据。

多进程追加写，I/O 出任何问题都不上报不重试。名字里带「科研线」的东西，没有资格碰主链路。

到手样本长这样（中段截断）：`1D0A628C****M5KD92`——26 位大写字母数字，不是 hex，字符集比 hex 宽。分析脚本预备了几个方向：字符集和长度分布、相邻样本的差异位、base32/base36 编码里嵌时间戳的可能性。判定分支也提前写好：前缀稳定尾部时变，就主攻时间戳还原；样本全是随机结构，就转向 B 线的泄漏面；B 线抽到和照片里相同的值，泄漏证实，全自动的钥匙到手；两三个窗口下来 B 线无候选、C 线无结构，判定不可推导，科研线封存止损——照片签本来就是低成本的长期能力。

还有一条没做的事也记一下：原本设想过从群聊图片里自动采集别人发的二维码截图，这条被否了，不做。别人的截图、别人的 enc，采集它没有任何我自己的正当性基础。科研线只研究我自己签到的数据。

## 作业：另一半换了方言

签到那套走的是 mobilelearn 域的 JSON 接口，参数拼在 URL 里，返回带 `status` 字段。我原以为作业照葫芦画瓢，抓下来一看是另一个世界：作业链路在 mooc1 域，返回不是 JSON，是渲染好的 HTML 片段——列表直接端给你，自己拆。

鉴权也换了形状。进课中间页 `stucoursemiddle` 的 HTML 里藏着三个隐藏域：`enc`、`openc`、`workEnc`。名字都姓 enc，各管各的：作业列表要的是 `workEnc`，`enc` 换了个名叫 `stuenc` 陪跑，`openc` 单独走。第一次拼参数我用错了件，列表页回一句「无权限」，排查半天才发现三个 enc 是三把不同的钥匙。

提取本身也有个小坑：隐藏域的属性顺序不保证，`id` 和 `value` 之间可能夹别的属性，正则得容忍乱序：

```rust
// 属性顺序容忍：id 与 value 之间可能夹 name 等属性
let grab = |name: &str| {
    capture(&html, &format!(r#"id="{name}"[^>]*value="([^"]*)""#))
        .with_context(|| format!("课程中间页缺少 {name}（页面可能改版）"))
};
Ok(CourseEncs {
    enc: grab("enc")?,
    openc: grab("openc")?,
    work_enc: grab("workEnc")?,
})
```

列表接口全长这样，注意 `enc=` 位置放的是 workEnc：

```rust
let url = format!(
    "{}{WORK_LIST_PATH}?courseId={}&classId={}&cpi={}&ut=s&openc={}&enc={}&t={}&stuenc={}&isdisplaytable=2&pageNum={page}",
    self.mooc1_base, course.course_id, course.clazz_id, course.cpi,
    encs.openc, encs.work_enc, crate::util::now(), encs.enc

```

返回的 HTML 里，每条作业是一个 `<li>`，详情 URL 整个塞在 `data` 属性里，标题和状态是里面的两个 class。拆法没有更高明的地方，就是正则：

```rust
let re_li = regex::Regex::new(r#"(?s)<li[^>]*data="([^"]+)"[^>]*>(.*?)</li>"#)?;
```

分页信息也不在 JSON 字段里，页面里直接写着一句 `pageNum : N`，正则抠出来翻页，上限夹到 10 页，防的是平台哪天返回异常数据，把轮询打爆。

## 截止时间没有年份

作业列表只有状态，没有截止时间。截止在详情页，渲染格式是「作答时间: MM-DD HH:MM 至 MM-DD HH:MM」——对，没有年份。学期九月开始，作业可能截止在次年一月，跨年作业的年份只能自己补。

补法是个保守推断：拿今年、明年、去年三个候选年份挨个套进 MM-DD，取距今不超过 180 天的那个。180 天比一个学期长、比一年短，跨年作业和放了一年的陈年作业就区分开了：

```rust
for year in [current, current + 1, current - 1] {
    let Ok(date) = chrono::NaiveDate::parse_from_str(
        &format!("{year}-{}", &end_mmdd[..5]), "%Y-%m-%d",
    ) else { continue };
    if (-180..=180).contains(&(date - today).num_days()) {
        return Some(year);
    }
}
```

## 作业只跟踪，不代答

轮询是个状态机。每个作业第一次见到，存一份快照（课程、标题、状态、首次见到的时间）；之后每轮对比状态字段，「未交」变「已交」的那一轮，把当初创建的待办自动勾掉。待办 id 就存在快照里，回写走 CAS，并发下改坏了也只是回勾精度受损，不会勾两次。

判断未交的方式朴素得可靠：平台状态是中文文案，未交的状态串里必然有个「未」字，找它就行。

提醒全走告警键去重：新作业只报一次，临期和过期各自按「类别、日期、作业」做键，一天最多提醒一次。通知系统最怕的不是漏报，是重复的噪音把人逼到关通知。

请求预算也压过：每门课每轮两个只读请求（中间页加列表），详情页只对未交的作业拉。截止时间一旦拿到就存进快照，之后轮询不再碰详情页，老师中途改截止这种情况检测不到。这是有意取舍，每个作业每轮省一次请求，比多盯一个低频事件值钱。

落盘和智慧树那边对齐：一门课一个索引文件，未交的作业各建一个文件夹写作业说明；已交的作业目录是纯噪音，索引里降级成一行文本。几个平台的作业最后在学期级的作业总表里汇成一张表，一条命令出全貌。

红线只有一条：作业只提醒、跟踪、归档，不做自动作答。自动答题就是代写，这个边界不碰。技术上题目接口不会比签到难，不做不是做不到。

## 收尾

现在的状态：上课前后机器人自己盯窗口，能自动签的五种形态当场签掉、回执到 QQ；二维码来了手机拍一张发过去，十几秒收到 ✅；手势被风控拦过一次，滑块管线顶了回去；作业到点提醒、交完自动销账。

这篇记下的东西，除了协议本身，更想留下的是三次「不信」：不信搜索结果标着的「活跃」，查了 pushed_at；不信社区流传的「enc 不校验」，虽然第一次是信了才栽的；不信「能自动就尽量自动」——拒绝重试、作业不代答、科研线只采自己的数据，这些边界不是能力不够，是不想让一个签到机器人变成别的东西。

图书馆那本借不了的书还在追书列表里。学习通这边，至少一门课里最磨人的两件事——签到和作业——机器人接手了。
