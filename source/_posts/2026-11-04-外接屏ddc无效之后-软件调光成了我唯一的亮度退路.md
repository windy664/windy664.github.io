我的主力显示器是一块 HDMI 外接屏，Omarchy 装好后我发现按键盘亮度键，屏幕一点反应都没有。不是键盘没绑定，是这台显示器压根不响应 DDC/CI 协议，系统没法通过软件指令去调它的背光。笔记本内屏还能走 `brightnessctl`，但日常我主要用外接屏，内屏基本合着。

这就把问题推到了一个很尴尬的位置：硬件调光的路断了，只能转向软件调光。软件调光不是调背光，而是调 gamma——把整个屏幕的伽马曲线压暗，视觉上亮度就降下来了。这条路走得通，但副作用也明显。这篇记我怎么用 `wl-gammarelay-rs` 补上外屏亮度控制，以及 gamma 调光带来的两个尾巴。

<!-- more -->

##  DDC 这条路先确认断在哪

Omarchy 的亮度脚本 `/usr/bin/omarchy-brightness-display` 对三类显示器有对应策略：

- 内屏（`eDP`/`LVDS`/`DSI` 开头）：走 `brightnessctl` 调背光；
- 外接屏：走 `omarchy-brightness-display-ddc`，底层是 `ddcutil`；
- Apple 显示器：走单独的 Apple 通道。

我的外接屏被识别为 `HDMI-A-1`，脚本自然会尝试 DDC。我用 `ddcutil detect` 看它的响应：

```
$ ddcutil detect
Invalid display
   I2C bus:  /dev/i2c-4
   DRM_connector:           card2-HDMI-A-1
   EDID synopsis:
      Mfg id:               AX@ - UNK
      Model:                A27
      Product code:         41511  (0xa227)
      Serial number:        
      Binary serial number: 1 (0x00000001)
      Manufacture year:     2025,  Week: 38
```

`Invalid display` 就是终审判决：这块屏的 DDC 接口要么没接线，要么固件不开放，系统级别没有任何调节背光的入口。加上这块屏的物理 OSD 菜单很难用，每次想调亮度都要伸手去摸五向键，非常打断节奏。

##  wl-gammarelay-rs 作为后备方案

`wl-gammarelay-rs` 是一个监听 wlr-gamma-control-unstable-v1 协议的小守护进程。它不碰背光，而是向 compositor 提供一套 gamma ramp，把红绿蓝三通道的输出值乘以一个系数。系数为 1 时画面原样输出，系数为 0 时三通道全灭，屏幕就黑了。视觉上这就等同于亮度调节。

它通过 D-Bus 暴露属性，最常用的是 `Brightness`：

```bash
$ busctl --user get-property rs.wl-gammarelay / rs.wl.gammarelay Brightness
d 0

$ busctl --user introspect rs.wl-gammarelay / rs.wl.gammarelay
NAME               TYPE     SIGNATURE RESULT/VALUE FLAGS
.ToggleInverted    method   -         -            -
.UpdateBrightness  method   d         -            -
.UpdateGamma       method   d         -            -
.UpdateTemperature method   n         -            -
.Brightness        property d         0            emits-change writable
.Gamma             property d         1            emits-change writable
.Inverted          property b         false        emits-change writable
.Temperature       property q         6500         emits-change writable
```

`Brightness` 是一个 `double`，范围大致是 0 到 1 以上。我测试时把它设到 0 能让屏幕全黑，设回 1 恢复正常。平时想调暗一点，就设成 0.6、0.4 之类的值。

把它加进开机自启动：`~/.config/hypr/autostart.lua` 里加一行：

```lua
o.launch_on_start("wl-gammarelay-rs")
```

这样登录后它就在后台跑着了，D-Bus 接口随时可用。

##  把亮度键接到 gamma 上

Omarchy 自带的亮度脚本其实已经为这种情况留了钩子。`/usr/bin/omarchy-brightness-display` 除了走 DDC 和内屏背光，还实现了一对 `off` / `on` 命令，专门用 `wl-gammarelay-rs` 把屏幕压到全黑或恢复：

```bash
# Fake blank: drive the panel to black through wl-gammarelay-rs instead of a
# real DPMS disable. A real DPMS-off on the last output makes Hyprland drop all
# outputs, which breaks the omarchy shell (background layer returns at alpha 0,
# or quickshell aborts outright -- omacom/omarchy#12554).
gamma_state="${XDG_RUNTIME_DIR:-/tmp}/omarchy-fake-blank.brightness"

gamma_set() {
  pgrep -x wl-gammarelay-rs >/dev/null 2>&1 || { setsid wl-gammarelay-rs >/dev/null 2>&1 & sleep 1; }
  busctl --user set-property rs.wl-gammarelay / rs.wl.gammarelay Brightness d "$1" >/dev/null 2>&1
}

gamma_get() {
  busctl --user get-property rs.wl-gammarelay / rs.wl.gammarelay Brightness 2>/dev/null | awk '{print $2}'
}

if [[ $step == "off" ]]; then
  cur="$(gamma_get)"
  [[ -n $cur ]] && printf '%s\n' "$cur" > "$gamma_state"
  gamma_set 0
  exit 0
elif [[ $step == "on" ]]; then
  cur="$(cat "$gamma_state" 2>/dev/null)"
  [[ -n $cur ]] || cur=1
  gamma_set "$cur"
  rm -f "$gamma_state"
  exit 0
fi
```

这段代码原本是为了做"假熄屏"：锁屏后不把显示器 DPMS 关掉（那会触发 quickshell 背景图层 alpha=0 的 bug），而是把 gamma 压到 0，屏幕看起来黑了，信号和 shell 都还在。我在月初那篇《把主力机换成 Omarchy 的这四天》里已经详细写过这个故事。

但这段代码也给了我灵感：既然 `gamma_set` 能把亮度压到 0 再恢复，日常调光为什么不能走同一条路？于是我把亮度键的处理接到了 gamma 上。按降低亮度键时，不再去尝试 DDC，而是直接读取当前 `Brightness` 值，减一个步长再写回去。升高亮度键则反向加。没有 OSD 显示百分比，但屏幕会实时变化，够用了。

##  软件调光不是免费午餐

gamma 乘法有几个绕不过去的副作用。

第一，它改变的是像素输出值，不是背光功率。亮度降到很低时，低灰阶会被压得更低，暗部细节容易糊成一片；亮度稍微回来一点，又可能因为色阶拉伸让颜色看起来格外"艳"。这就是用户常说的"过饱和"——其实不一定是饱和度真的被调高了，而是 gamma 曲线被压后，中亮部相对更突出了。

我遇到的情况是：白天主题一切到浅色，浏览器和 QQ 的颜色突然变得刺眼。起初我以为是 gamma 调光把颜色搞坏了，排查后才发现真凶是 Omarchy 的昼夜主题定时器。早上 7 点它把主题切到 `catppuccin-latte`，浅色壁纸、浅色终端、浅色顶栏一起涌上来，视觉上对比度暴增，让我误以为是过饱和。我把终端钉死深色、顶栏用覆盖层固定毛玻璃效果后，这个现象才消失。

这件事让我学会区分：gamma 调光会让暗部压缩，但大范围"过饱和"往往要先怀疑主题切换。

##  视频全屏黑屏的悬案

另一个没结的案子是：看视频时一按全屏，屏幕会突然全黑，几秒钟后 NVIDIA 弹出通知。那段时间我正好在调 gamma，第一时间怀疑是 `wl-gammarelay-rs` 的 `Brightness` 被什么触发放到了 0。

我当时的排查思路是：

1. 检查 `Brightness` 属性是不是变成了 0；
2. 检查锁屏的 `idleBlankTimer` 是否误触发（只在锁屏界面生效，排除）；
3. 检查 `wl-gammarelay-rs` 是否还活着（pid 常驻，排除崩溃）；
4. 检查 HDMI 的 DDC 是否有延迟响应导致误判（DDC 本身无效，排除）。

但干扰因素太多：我自己在测试时也按过亮度键，把 gamma 打到了 0，那几次黑屏可能是我自己的操作，不能算作物联网的自动触发。后来我也没有稳定复现"视频全屏必黑"。所以这个案子暂时挂在未决列表里。

现在我的假设是：某些全屏切换路径会短暂让 `wl-gammarelay-rs` 失去对输出的控制，或者某个应用在全屏时主动请求了 gamma=0。下次再出现，我需要记录三件事：鼠标动一下能不能恢复、是整个屏幕黑还是只有视频区域黑、以及 `busctl` 读出来的 `Brightness` 当时是多少。

##  笔记本内屏和外屏的混合策略

现在我的亮度控制分两条路：

- 内屏（`eDP-1`）：继续走 `brightnessctl`，这是真正的背光调节，没有 gamma 副作用；
- 外接屏（`HDMI-A-1`）：DDC 无效，走 `wl-gammarelay-rs` 的软件调光；
- 锁屏/睡觉时：外屏也走 `wl-gammarelay-rs` 的 `off` 命令做假熄屏，避免 DPMS 触发 quickshell bug。

`omarchy-brightness-display` 脚本里的逻辑正好对应这三种场景：内屏用背光、外屏尝试 DDC失败后 fallback、假熄屏统一走 gamma。我只是在 fallback 这一步把 DDC 失败直接接到了 gamma 调光上，而不是让用户按亮度键没反应。

##  复盘

这件事从头到尾都不是一个优雅的解法。DDC 无效是硬件层面的遗憾，gamma 调光是软件层面的妥协。它的代价是你要接受颜色可能轻微漂移、暗部可能压缩、以及全屏视频时那桩还没破的黑屏悬案。

但对我来说，这条路仍然比每次伸手去摸显示器 OSD 强。而且因为它走的是 wlr-gamma-control 协议，理论上任何 Wayland compositor 都能用，不绑定 Omarchy。如果以后换到 sway、river 或者 Hyprland 主线，同样的 `wl-gammarelay-rs` 命令还能继续用。

唯一的建议是：如果你也打算用 gamma 调光，别把亮度压到 0 当常态。gamma=0 适合假熄屏，不适合阅读。日常我把它维持在 0.5 到 0.8 之间，眼睛舒服，副作用也不明显。真遇到颜色不对劲，先 `busctl --user get-property rs.wl-gammarelay / rs.wl.gammarelay Brightness` 看一眼，排除 gamma 被意外调低的可能，再去找主题或应用自己的锅。
