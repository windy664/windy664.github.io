校园数据源里，课表的地位很特殊。图书馆出错，少推送几本书；作业出错，晚提醒一条；课表出错，是地基下沉。我的签到轮询踩在课表上，智慧树的课程目录按课表短名做归一化，每天的上课提醒、`/日程` 的合并视图，全都从它来。课表错一周，这三个东西跟着错一周。

这次拆的就是课表背后的正方教务系统。正方大概是国内高校装机量最大的教务系统，年岁不小，老到什么程度后面会讲。先给结论：它是几个校园平台里协议最老派的一个，无填充 RSA、算术验证码、二十分钟就过期的票据；但也是我最不担心的一个。老派的另一面是老实，协议写完就不变了，这对写自动化的人反而是好事。

## 两个门牌，先走对

动手前先认门。学校给学生用的入口是网上一站式事务大厅，很多人第一反应是从这里进去。实际上事务大厅只是个壳，本身不承载数据，课表在教务系统自己的域名底下。逆向的第一个决定就是绕开大厅，直连教务。

直连还有个意外的坑。教务有个自己的登录页，我拿统一认证的账号密码去试，返回「用户名或密码不正确」。不是账号错了，是这套直登页的密码体系跟统一认证不是同一套，两边密码可以不同。浏览器里翻会话记录，看到真实链路是先去统一认证换票，再拿着票跳教务。也就是说正确路径只有一条：统一认证 CAS 换票，教务收票建会话。

## CAS 三步票务

统一认证是个 CAS 服务，走 REST 接口，全程三步：

| 步骤 | 请求 | 拿到什么 |
| --- | --- | --- |
| 一 | `POST /v1/tickets`，密码加密后随表单提交，带算术验证码答案 | TGT 和一张 ST |
| 二 | `POST /v1/tickets/<TGT>`，body 里带上服务地址 | 响应体直接就是新的 ST 字符串 |
| 三 | `GET <教务域名>/sso/lyiotlogin?ticket=<ST>` | 一串 302，落进教务会话 |

先说怎么找到这套接口的。统一认证前端是个 React 单页应用，页面上没有任何表单提交的痕迹，抓包才看到真正干活的是打包后的 app 脚本在发 REST 请求，全程 form-urlencoded，跟教科书里那种重定向满天飞的老式 CAS 完全两个物种。

第二步的设计第一眼很容易错过。换票的响应不包 JSON，没有壳，body 就是票本身。我第一回对接的时候按 JSON 解析，报错说解析失败，盯着返回看了半天才发现票就躺在那里。

第三步的跳转链值得记录，因为排查时要靠它定位断在哪一节：

```
<教务域名>/sso/lyiotlogin?ticket=<ST>
  → /jwglxt/ticketlogin?uid=..&timestamp=..&verify=..
  → login_slogin.html
  → index_initMenu.html?jsdm=xs&_t=..&echarts=1
```

四节 302 走完，教务域下的会话 cookie 才落袋。这条链还有个古怪的脾气：偶发抖动，同一个 TGT 上一分钟验票失败，下一分钟自己又好了。头一回撞上以为是自己代码的并发问题，重放几次才发现是服务端的。应对也简单，客户端做一次四百毫秒间隔的短重试，重试还失败就把最终状态码带进错误信息，方便下次诊断。

CAS 的报错码倒是规整：密码错是 `FALSE`，验证码错是 `CODEFALSE`，查无此人是 `NOUSER`，锁定是 `USERLOCK`，禁用是 `USERDISABLED`，还有要二次验证的 `TWOVERIFY`。写重试逻辑之前先把这张表摸清楚，哪个码该重试、哪个码碰都不能碰，后面会讲这为什么重要。

## 密码是拿手算的：Ohdave 裸 RSA

技术含量最高的一段来了。CAS 前端给密码加密用的还是 Ohdave 的 BigInt.js，一个十几年前的浏览器端 RSA 加密库。它没有填充，没有随机数，就是教科书式的裸 RSA：把密码字符串当成一个大整数，直接做模幂。

它有几条很任性的规矩。密码按块处理，块大小是模长相关的两倍十六进制组数；每块按小端序把字符编码打包成字节；每块单独做 `m^e mod n`；输出结果按十六位一组倒序转成十六进制，每组固定四位宽度，多块之间用单个空格连接。哪一条跟主流实现都不太一样，漏掉任何一条服务端都解不开。库的入口还有个经典魔数 `setMaxDigits(131)`，是给那个手写 BigInt 实现预分配数组用的，看到这行就知道这代码的辈分了。

为了不靠猜，我把这段逻辑先用 Python 移植了一遍，拿页面里的 JS 跑一份密文，再拿移植版跑同一份明文，逐字节对照，全部对上之后才敢往 Rust 里写。核心代码不长，贴出来：

```rust
pub fn ohdave_encrypt(text: &str, exponent_hex: &str, modulus_hex: &str) -> String {
    let exponent = BigUint::from_str_radix(exponent_hex, 16).expect("invalid RSA exponent");
    let modulus = BigUint::from_str_radix(modulus_hex, 16).expect("invalid RSA modulus");
    // h(modulus)：最高非零 16-bit digit 下标（4 个 hex 字符一组，自高位起）
    let groups: Vec<u16> = modulus_hex
        .as_bytes()
        .chunks(4)
        .map(|chunk| {
            u16::from_str_radix(std::str::from_utf8(chunk).unwrap_or("0"), 16).unwrap_or(0)
        })
        .collect();
    let highest = groups.iter().rposition(|g| *g != 0).unwrap_or(0);
    let chunk = 2 * highest;

    let codes: Vec<u32> = text.chars().map(|c| c as u32).collect();
    let mut blocks = Vec::new();
    for offset in (0..codes.len()).step_by(chunk.max(1)) {
        let slice = &codes[offset..(offset + chunk).min(codes.len())];
        let mut bytes = vec![0u8; chunk];
        for (index, code) in slice.iter().enumerate() {
            bytes[index] = (*code & 0xFF) as u8;
        }
        let m = BigUint::from_bytes_le(&bytes);
        let c = m.modpow(&exponent, &modulus);
        blocks.push(limb_hex(&c));
    }
    blocks.join(" ")
}
```

输出宽度那条规矩单独写了一个函数，模幂结果的十六进制要按十六位一组倒序补零，宽度是「最高非零组下标加一」乘四：

```rust
fn limb_hex(value: &BigUint) -> String {
    if value.is_zero() {
        return "0000".to_owned();
    }
    let bytes = value.to_bytes_le();
    let mut limbs = Vec::new();
    for chunk in bytes.chunks(2) {
        let low = chunk[0] as u16;
        let high = chunk.get(1).map(|b| (*b as u16) << 8).unwrap_or(0);
        limbs.push(low | high);
    }
    while limbs.last() == Some(&0) {
        limbs.pop();
    }
    limbs.iter().rev().map(|limb| format!("{limb:04x}")).collect()
}
```

两个固定口令的测试向量留在单元测试里，跟浏览器里 JS 的输出一字不差。正方没有让你猜，它只是把一个 2010 年的前端加密库原封不动跑到了今天。

## 验证码是道算术题

这套 CAS 强制图形验证码，而且发的不是歪歪扭扭的字母，是算术题。拉验证码的接口是 `GET /kaptcha?uid=<客户端生成的uuid>`，返回一段 JSON，里面 `content` 字段是张一百乘二十五像素的彩色 PNG，base64 塞在 data URI 里，图上印着类似 `8 * 7 =` 的式子。提交的时候答案填 `code`，拉验证码时那个 uuid 填 `id`，服务端靠它对号。把式子识别出来，算出得数，随登录表单提交。

识别走了离线模板匹配的老路：亮度阈值二值化，列投影切成四个字形，归一化成十二乘十六的位图，跟模板库算汉明距离取最近邻。彩色验证码里的浅色字形亮度能到二百三十六，阈值卡在二百四十五才切得干净。认不出的判据是距离超过四十八就拒答，让调用方换一张图重来，宁可多拉一次也不交错答案。

```rust
fn classify(glyph: &Glyph) -> Option<char> {
    let (ch, distance) = GLYPH_TEMPLATES
        .iter()
        .map(|(ch, tpl)| (*ch, hamming(glyph, tpl)))
        .min_by_key(|(_, d)| *d)?;
    (distance <= REJECT_DISTANCE).then_some(ch)
}
```

模板库的来历比较笨但可靠：抓了四十张真验证码，人工把每张的算式标注一遍，从这些样本生成字形模板。留一交叉验证，四十张全部算对。校方哪天换了验证码风格，重新抓样本、重新标注、重新生成模板就行，管线不用动。

顺手做了个探针实验。社区传说登录接口带某个参数能跳过验证码，我拿 `loginType=1` 试了：验证码确实不弹了，但账密直接被拒，返回密码错误。也就是说免验证码通道根本不存在，服务端只是把验证码校验挪到了账密校验前面。别信传说，花十分钟自己探一遍就死心了。

## 票据只活二十分钟

拿真实环境测出来的数字：TGT 的有效期在二十到四十五分钟之间浮动，教务会话闲置半小时左右过期。这个寿命对轮询服务很不友好，你不能指望登录一次管一周。

所以架构上的取舍是把登录做成例行操作，而不是兜底手段。常态流程是：手头有 TGT 就先换 ST（这一步免验证码），换不到票再走完整的验证码登录。验证码求解器是这条链路里唯一需要「动脑子」的环节，前面说了，它是个纯离线的模板匹配，毫秒级出答案。与其祈祷会话活着，不如让重新登录这件事便宜到没人会在乎。

## 课表接口和它的黑话

会话建好之后，课表数据就一个接口：`POST /jwglxt/kbcx/xskbcx_cxXsgrkb.html?gnmkdm=N2151`。表单里两个关键参数，`xnm` 填学年，`xqm` 填学期。学期不是填一二三，是填 `3`、`12`、`16`。这组魔法数字没有任何文档解释，三个值对应三个学期，纯靠试。我的推断逻辑写在代码里，按当前月份猜默认学期，配置文件可以覆盖。

返回的 `kbList` 一次给整学期的课，顶层还跟着一份 `xsxx`，装着学年、学期、学号、姓名、班级这些身份信息，等于顺手把「我是谁」也确认了一遍。每条记录里关键字段有课名、课程编号、星期、节次、周次、教室、老师。周次字段 `zcd` 是个位掩码式的字符串，比如「1,2,3,4,5周」，另有 `oldzc`、`oldjc` 两个旧值字段常年在返回里躺着，后面会讲它们怎么坑过我一次。课表页面本身只有一个渲染视图，没有按周查询的参数，想看第几周还是要靠客户端自己算。没登录去调这个接口，不会报错，直接 302 跳登录页。这一点反过来成了最好用的登录态探针：跳了就是掉线了，没跳就是还活着。

## 周次要自己算，也真的算错过

接口不告诉你今天是第几周，这得自己拿校历推。逻辑一行：

```rust
pub fn week_of(semester_start: NaiveDate, date: NaiveDate) -> i64 {
    (date - semester_start).num_days().div_euclid(7) + 1
}
```

代码没出过错，出过错的是 `semester_start` 这个配置值。最早的锚点是九月七日，当时写进侦察文档的推理是：全校没有任何一门课排在第一周，所以第一周周一应该是九月七日。听着挺有道理，毛病是用缺失的证据当了依据。十一月用户一句话戳穿：现在是第十周了。一查，军事理论课排在第二到三周，而军训恰好是九月七日到二十二日，军理是接在军训后面上的课。倒推回去，校历第一周周一是八月三十一日。

改的东西是一行配置，付的学费不小。之前偶尔出现「今天没课也发了提醒」的幽灵提醒，破案后发现全是这一天的偏差造成的，日期错一周，该上的课和真实的课对不上，提醒自然错位。侦察文档里现在有一行加粗的警告，原话是：不要从某条 `zcd=第N周` 的记录反推今天是第 N 周，那是行课计划，不是当前周。

## 变更检测：一行签名

盯课表的核心是回答一个问题：今天跟昨天比，课表变没变。我的做法是给每节课算一个稳定签名，把课程编号、星期、节次、周次、教室、老师用竖线拼起来：

```rust
pub fn signature(&self) -> String {
    format!(
        "{}|{}|{}|{}|{}|{}",
        self.course_id,
        self.weekday,
        self.sections_raw,
        self.weeks_raw,
        self.classroom,
        self.teacher
    )
}
```

粒度故意切得细：同一门课换个教室、挪一周，签名就变了，都算变更。每次拉到课表，先对全体签名算个哈希，跟快照里存的哈希一样就直接走人，不一样才做逐条比对：

```rust
let old_sigs: HashSet<String> = old.meetings.iter().map(stored_signature).collect();
let mut changes = Vec::new();
for meeting in meetings {
    let sig = &meeting.signature();
    if !old_sigs.contains(sig) {
        changes.push(format!(
            "**新增** {}｜{}周｜{}｜{}｜@{}",
            meeting.course,
            meeting.weeks_raw,
            WEEKDAY_NAMES[(meeting.weekday as usize).clamp(1, 7) - 1],
            when(meeting),
            meeting.classroom
        ));
    }
}
```

旧的集合里反过来再扫一遍，消失的签名就是被取消的课。新增取消分开报，告警按同日去重，教务中午改一次下午又改一次，也只提醒一遍，不会把人轰炸两遍。到点还有一道每日推送，把明天的课表整理好发过来，同样按日期做了每日一次的闸。平时在 QQ 里问 `/课表`、`/明日课表`，读的是本地缓存快照，不回源打教务，查询再频繁也只是一次读库。

这中间还修过一个自己的 bug。课表关键词的模糊匹配一度太贪，把通知类消息也当成课表查询吞掉了。修法是两道闸：长度加一道，真人的查询都是「明天有什么课」这种短句，长文本直接不进课表逻辑；再加通知特征词否决。改动小，但教训跟前面验证码那段一个道理：匹配逻辑要给误伤留出口。

## 登录成功之后的五天

讲一场排查了五天的怪病。日志里连续五天 `login_ok: false`，细看不是登录失败：CAS 登录成功，票也换到了，教务的会话跳转链一节不落全走通了，最后课表接口永远被踢回登录页。

排查工具链值得记一笔。先用 `getent ahostsv4` 对比宿主机和容器各自把教务域名解析到了哪个地址，两边不一致；再拿 `curl --resolve` 把域名手动钉到候选地址上，把整条 SSO 链人肉走一遍；最后 `docker exec` 进容器，用守护进程完全相同的参数手动触发一次轮询。根因找到了：容器的 `ExtraHosts` 里躺着一条历史遗留的地址钉子，钉的是教务的旧版节点。旧节点还活着，访问根路径返回二百，看起来「域名是通的」，但它上面已经没有课表接口，新接口一律四百零五。CAS 和票务走的是另一个域名，所以全通；课表接口走被钉死的旧地址，所以永远进不去。

中间还踩了一个更隐蔽的坑：手动排查时不带数据库参数跑了一次，程序读到一个空库，报出来的登录状态跟线上完全对不上，照着假象又白绕了一圈。排查容器里跑的服务，参数要跟守护进程一字不差，不然你查的是另一个平行宇宙。

## 「课表更新了你自己没去看吗」

上个月的另一次对峙。我这边日志显示连续七十二小时变更数为零，用户那边说课表明明更新了。谁错？

取证走了四步。第一步，从容器里的会话直接调教务接口，拿原始返回；第二步，把返回的三十行课表跟本地快照逐行比对，一致；第三步，复查 diff 逻辑，确认没有静默丢行的路径；第四步，确认 `oldzc`、`oldjc` 那两个常年躺着的旧值字段是正方的常态字段，不是什么调整信号。四步做完，结论成立：接口说没变，就是没变。

用户看到的「更新」是这么来的：一批课的开课周本来就是第十周起，到点之后它们第一次出现在日历视图里。数据一天都没变，变的是日历上多出来的几节课。这事跟验证码探针凑成了一对经验：社区传说不信，自己的怀疑也要验，接口的返回是唯一证人。

## 密码错一次就停手

这台 CAS 有失败计数和账号锁定，密码错几次账号直接锁死，锁了就得走人工流程。所以模块里有一条比任何功能都优先的规矩：密码类错误零重试。`FALSE`、`PASSERROR`、`USERLOCK` 这几个码一出现，登录流程立刻收手告警，等人来看。允许自动重试的只有验证码识别失败这一种，换张图再来，单轮最多三张，超过就停。自动化的边界要分清楚：识别错误可以自己纠，凭证错误必须交还给人，机器替人猜密码是要出事的。

顺带两条自我约束一起交代。一是只读，这条线只拉课表，选课、评教、成绩查询一律不碰，写操作的接口分析得再明白也不去调，教务系统里一个误操作是真的会影响选课结果的。二是凭证管理，账号密码只放在 gitignore 掉的本地配置和环境变量里，登录态文件同等对待，不进代码库也不进笔记仓库。逆向归逆向，逆向的产出是协议文档，不是别人的账号。

## 收尾

几个校园平台拆下来感受很不同。图书馆接口免登录公开，像没锁门的自习室；学习通全是明文请求加 JSON，简单直白；智慧树又是加密又是环境校验，处处设卡。正方是另一种气质：无填充 RSA、算术验证码、二十分钟的票据、没有绕行的验证码通道，看着戒备森严，其实没有风控，没有行为检测，没有浏览器指纹校验，协议从十年前定稿到今天一个字没动过。对自动化来说，一个不变的协议比一个热情的协议好用得多。

课表这条线还有个别人没有的属性：它是所有校园附属里唯一「错一周就全错一周」的。所以它的变更检测做得比谁都严，签名、快照、哈希三道闸，登录探针每天先探一次。地基不晃，上面盖的东西才敢往上摞。
